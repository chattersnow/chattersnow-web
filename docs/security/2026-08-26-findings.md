Scope: RLS policies, Supabase auth flow, public routes, dependency scan, standard web checks (per issue #241). This document records findings only; fixes are tracked in the linked follow-up issues.

## 1. No role-based access control — HIGH

**Area:** `supabase/migrations/20260819000000_create_donations_and_inventory.sql`, `supabase/migrations/20260819010000_create_events_table.sql`

**Finding:** Every RLS policy in both migrations is the same shape:

```sql
create policy "authenticated full access" on public.<table>
  for all to authenticated using (auth.uid() is not null) with check (auth.uid() is not null);
```

This applies to `donors`, `donations`, `inventory_items`, `inventory_movements`, and `events`. There is no `profiles`/`roles`/`user_roles` table and no role check anywhere in the policies, server actions, or page guards — every page and Server Action in `src/app/portal/**` only checks "is there a signed-in user," never "does this user hold the required role."

The spec (`docs/technical-spec.md` §5.3, §7.3) explicitly calls for role-scoped access ("the initial portal role is `admin`"; "authenticated users should receive only the permissions associated with their roles"), and the identity/access data model in §6 expects `profiles`/`roles`/`user_roles` tables that don't exist yet.

**Reproduction:** Any account that can complete authentication against the Supabase project (see finding 3) can run, e.g.:

```js
const { data } = await supabase.from("donors").select("name, email, phone, notes");
```

and receive every donor's PII, with full insert/update/delete rights on the same and every other portal table — there is currently no such thing as a lower-privilege portal account.

**Suggested follow-up:** Introduce `profiles`/`user_roles` and rewrite the RLS policies to check role membership, not just `auth.uid() is not null`, before granting portal accounts beyond a single trusted admin.

## 2. Open redirect on OAuth callback — MEDIUM

**Area:** `src/app/auth/callback/route.ts:9`

```ts
const destination = next?.startsWith("/") ? next : "/portal/home";
```

**Finding:** `next` is taken verbatim from the query string. `startsWith("/")` also matches protocol-relative URLs like `//evil.com`, which `new URL("//evil.com", requestUrl.origin)` resolves to `https://evil.com/`. An attacker who sends a victim a Google-sign-in link through this app with `?next=//evil.com` gets the victim redirected to an attacker-controlled site immediately after they authenticate — a classic post-login open redirect (CWE-601), useful for phishing/credential harvesting that looks like it follows a legitimate sign-in.

**Reproduction:** Start the Google OAuth flow with `redirectTo` pointing at `/auth/callback?next=//attacker.example`; after a successful login, the response redirects to `attacker.example` instead of staying on-site.

**Suggested follow-up:** Validate `next` more strictly — e.g. require it to parse as same-origin (`new URL(next, requestUrl.origin).origin === requestUrl.origin`) rather than a naive prefix check, and reject anything else.

## 3. Open self-signup in local auth config — MEDIUM (needs production verification)

**Area:** `supabase/config.toml` (`[auth]` / `[auth.email]`)

**Finding:** The local dev Supabase config has `enable_signup = true` at the top level and under `[auth.email]`, with `enable_confirmations = false`. This is the local dev stack config per project convention, not necessarily the production project's settings — but if the hosted Supabase project mirrors it, anyone can create an account by email/password with no confirmation step, and (per finding 1) that account gets full portal data access immediately. This wasn't independently verified against the production Supabase dashboard as part of this static review.

**Suggested follow-up:** Confirm in the Supabase Cloud dashboard for the production project that email/password self-signup is disabled (or gated) and that Google OAuth is restricted appropriately, independent of fixing finding 1.

## 4. Free-text input not format-validated — LOW

**Area:** `src/app/portal/home/actions.ts` (`createDonationAction`), similar patterns in `events/actions.ts` and `inventory/actions.ts`

**Finding:** Enum-like fields (`sourceType`, `condition`, `status`, `visibility`) are validated against whitelists, but free-text fields like `donorEmail` and `donorPhone` are only trimmed, not checked for a plausible email/phone shape. Not exploitable (values are passed as bound RPC/query parameters, not concatenated into SQL), but it's a gap against spec §7.8's request for shared-schema input validation and could let obviously-malformed contact data into `donors`.

**Suggested follow-up:** Add lightweight format checks (or a shared zod-style schema) for email/phone fields shared between the client and the Server Action.

## 5. Storage buckets not yet in scope — INFO

**Area:** `supabase/config.toml` (`[storage]`)

**Finding:** No buckets are configured; `inventory_items.photo_url` currently stores external Google Drive share links, resolved client-side in `inventory-shared.tsx`. Spec §7.5 (private-by-default buckets, signed URLs for authorized files) doesn't apply yet because Storage isn't in use. Flagging so it's re-checked once photos move into Supabase Storage.
