# Accessibility scan findings (issue #240)

Findings-only audit against WCAG 2.1 AA. Automated scan tool: `e2e/a11y-scan.ts` (axe-core via Playwright, tags `wcag2a`/`wcag2aa`/`wcag21a`/`wcag21aa`), run against 24 public routes and 42 portal routes (signed in as `admin@example.test`) on top of `development` as of 2026-08-27. Raw output: `e2e/a11y-report.json` (gitignored — regenerate with `bun run e2e/a11y-scan.ts` against a running `bun run dev` + seeded local Supabase stack; on a slow/synced filesystem, `curl` each route once first to force Turbopack to precompile it, or the scan's 30s per-page timeout can trip on first-compile).

Fixing findings is out of scope for this ticket; each finding below has its own follow-up issue.

## Manual spot-check

Keyboard-only tab-order and focus-visibility spot-checks on `/gears` and `/portal/governance/nonprofit-status` (heaviest finding-1 page): tab order is sequential and matches visual layout, all shadcn-based controls show a visible focus ring (`focus-visible:ring-3`), and the nested-interactive card/checkbox pair from finding 2 is reachable via keyboard (not a keyboard trap) — the defect is purely in the accessibility-tree semantics, not keyboard operability. No additional issues found beyond the findings above. A full manual screen-reader pass (VoiceOver/NVDA) across all routes was not performed in this session; the findings above are well-understood enough from the automated results and source inspection that a targeted re-listen isn't needed to file them, but a broader manual pass is still worth doing separately if deeper coverage is wanted.

## Next steps

Per the acceptance criteria: findings are triaged into the two follow-up issues above, each scoped to a single root cause/shared component so they can be picked up independently. Both are worth prioritizing since a single fix (in `select.tsx`'s usages, or the two badge tokens) resolves every listed route at once.
