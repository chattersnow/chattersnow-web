## 5.17 Volunteer management

Authorized users shall be able to track volunteer participation, per the "Volunteers — roles"/"participation" rows already named in the entitlement matrix ([§5.3](access-control.md#53-authentication-and-authorization)) and the reporting need described in `planning/drafts/BUSINESS_PLAN.md` §10–§11:

- A catalog of volunteer role types (e.g. Ride Buddy, Event Setup, Basecamp Staffing) that events can be tagged with.
- Volunteer profiles, reusing the existing `people` directory and its derived volunteer role rather than a separate contact record.
- Hours logging: person, optional event, date, hours, role type, and who logged the entry. The `volunteer` role may log and view their own hours; `admin` and `event_coordinator` may view all.

Volunteer hours feed the Impact Tracking rollups in [§5.15](programs.md#515-impact-tracking-and-reporting) (e.g. "290 volunteer hours" in a season report).

**Implemented** (issues #49/#50): `volunteer_role_types` and `volunteer_hours` back `/portal/volunteers/roles` and `/portal/volunteers/participation`, gated by the `volunteers` resource per [§5.3](access-control.md#53-authentication-and-authorization). As of 20260904010000 `volunteer_hours` is also what the event editor's Volunteers tab writes — `event_volunteer_hours` was folded into it — so that tab is now an event-scoped view of the same ledger and its entries flow into Participation, the person profile's Volunteer activity card, and the [§5.15](programs.md#515-impact-tracking-and-reporting) rollup. Event-scoped access is preserved through the surviving `event_volunteer_hours` resource key rather than a second table. The role-type view/edit flow (`role-type-details-dialog.tsx`) still uses the Dialog-based pattern rather than the Sheet-based pattern used elsewhere for viewing/editing an existing record (people, inventory, expenses, events) — see the convention note in [§8](../technical-spec.md#8-application-structure); this should be brought in line the same way as the Programs page ([§5.14](programs.md#514-program-management)).

**Implemented — public volunteer opportunities** (issue #60): `/get-involved/volunteer` reads live from `public_volunteer_role_types`, a curated view (`id`, `name`, `description` — no icon field) granted to `anon`/`authenticated` over `volunteer_role_types` rows flagged `is_public`, following the same pattern as `public_gear_catalog`/`public_events`. The hardcoded opportunities array is gone.

**Implemented — public volunteer application form** (issue #161): the same page also renders an application form backed by `volunteer_applications` (`person_id`, `name`, `email`, `phone`, free-text `role_interest`, `availability`, `status`: new/being reviewed/contacted/placed/declined/closed) and a `security definer` `submit_volunteer_application()` RPC. Applications are not auto-converted into `people`/volunteer records — they're triaged from the portal instead (see below). This is a separate intake path from the role-type catalog above — it captures interest, not a role assignment.

**Implemented — portal application queue** (issue #173): `/portal/volunteers/applications` lists submissions (search by name/email, filter by status), gated by the same `volunteers` resource as the rows above. A details sheet shows the full submission and, for `volunteers:manage` holders, an inline status control; view-only holders see the status as plain text. New (`status = 'new'`) applications are flagged in the notification bell and the dashboard's "Needs your attention" card, linking to the queue pre-filtered to `?status=new`. **Implemented — outbound notice** (issue #742): submitting an application also emails every opted-in `volunteers:manage` holder in that application's tenant, deep-linked to the application (`?application=<id>`, which opens its details sheet even when the row is not on the current page of the list). Recipients are resolved by `people_with_permission()`, the sessionless counterpart to `has_permission()`; the send is scheduled with `after()` so it cannot delay or fail the public submission.

**Implemented — writing to the applicant** (issue #1204, on the primitive from [#1203](inventory.md#54-inventory-and-donation-management)): the application sheet carries a Messages list and two actions behind `volunteers:manage` — **Message applicant**, which sends one message the reviewer types, and **Resend confirmation**, which re-renders the applicant's own receipt (issue #1069) for somebody who never received it or has lost the reference code they check their status with. The reviewer's first move is usually a question — about availability, about a role that would fit better, about a background check — and asking it from a personal mailbox left the next reviewer looking at an application with no record of what was asked or answered.

Nothing here is volunteer-specific below the surface: `outbound_messages` is polymorphic and its select policy is evaluated against each row's own `module`, so a volunteers manager reads an application's messages and none of another queue's, with no second policy and no migration. The address is resolved from the application by the Server Action rather than taken from the browser; replies leave the platform for the tenant's Reply-To mailbox, which the composer says; and a resend varies its dedupe key by the minute, so a second copy can go tomorrow while a double-click today is one email.

**Implemented — a volunteer logging their own hours** (issue #1165, epic #1160; the public copy removed in #1303): a volunteer holding `volunteer_hours_logging:manage` logs hours for themselves at `/portal/volunteers/participation`, which renders a self-log-only mode for somebody who can log their own hours but confirm nobody's. The same capability shipped on the public host at `/my/hours` and was withdrawn: it duplicated the portal's, with no view of what had been confirmed and a second set of RPCs and rate limits to hold in step. **Self-logged hours are provisional until a `volunteers:manage` holder confirms them.** Unreviewed hours feed impact reporting and reimbursements, and a number that reaches a funder without anyone having looked at it is the mistake with no way back; a short review queue is the cheaper failure.

The provisional state is a **separate table, `volunteer_hour_submissions`, not a status column on `volunteer_hours`**. A status column would mean every existing reader of the ledger — `get_event_impact_derived_data()`, `get_program_impact_rollup_data()`, Participation, the event roster, the person card, the role-flag trigger — had to remember a `where` clause it does not have today, and the one that forgot would be a silently inflated figure. With a table of its own a pending entry is simply not in the ledger: nothing that reports on hours changes, and nothing can accidentally include it. It is also the shape this schema already uses for public intake that staff review — `volunteer_applications`, `gear_requests`, `person_claims` all land in their own table and are promoted by a decision.

`review_volunteer_hour_submission()` is that decision, and the only thing that moves a submission into the ledger. Confirming writes the `volunteer_hours` row with **`logged_by` naming the volunteer**, not the reviewer, so the ledger records who actually did the hours; the reviewer is in `updated_by`. A reviewer may confirm a corrected number — a volunteer typing 8 for a six-hour shift is the ordinary case, and making them resubmit would read as a rejection — and the submission keeps what was claimed. A decline writes no hours and keeps the row, so the volunteer's own history can say "not confirmed" rather than losing four hours silently. The queue is a section on `/portal/volunteers/participation`, above the ledger and absent when it is empty, and the pending count is an ops-inbox item for `volunteers:view` holders. The entry is capped at 24 hours a day and one pending submission per person per day per event, the date is checked against the tenant's own day ([§6.1](../technical-spec.md#6-proposed-data-model)) rather than the server's, and the whole route is rate-limited per `(route, ip)` like every other public intake. The event picker (`my_loggable_events()`) offers the same set the write accepts: this tenant's published public events plus any the person signed up for or registered for.

**Implemented — recording a screening outcome** (issue #1360, the portal half of #690): `volunteer_screening_tiers` and `person_screenings` back `/portal/volunteers/screening`, a Screening card on the person profile and a read-only Screening section on the application sheet. Until this, `docs/spec/volunteers.md` could note that a reviewer's first question is often "about a background check" and that #1204 records the question, while nothing recorded the answer — so the only durable record of a completed check was whatever the reviewer remembered.

**What is stored is a level, a date, and optionally the date the clearance runs to.** Never the check results, never the underlying record, never a conviction and never a court reference. Three absences carry that, and each is the ticket rather than an omission:

- **No status column, and no "not cleared" row.** The row's existence is the outcome. A negative row would be a durable adverse record about a person, readable by everyone holding the permission, with nothing behind it the person could see or answer — the opposite of the screening policy's rule that a record is not automatically a bar and the person is told what came up and gets to respond. Where somebody is not cleared, `volunteer_applications.status` (`declined`, `closed`) carries the operational decision and the application's Messages carry the conversation; both are things the applicant took part in, and this table is not.
- **No free text of any kind** — no note, no reference, no provider, no result. Any text box here eventually contains a conviction, so the promise that check results never enter the portal is a _schema_ guarantee rather than a validation one, which is the only kind that survives a later ticket. `parsePersonScreeningForm` is an allowlist for the same reason and a unit test holds it to three fields; `created_by` and `cleared_on` answer "who decided and when" without prose, and the level's own `description` answers "what does this mean" once, on the catalog.
- **No single current row per (person, level).** A re-screen is a new row, not an edit, because "cleared for Tier 1 in 2026 and again in 2029" is exactly what a recheck schedule will need. A unique key on `(tenant, person, level, cleared_on)` catches only a double-tapped submit.

The level is a **tenant-owned catalog, not a platform enum and not free text**. Tiering is tenant vocabulary — one organization's "Tier 1" is another's "works with participants" — so an enum would be the platform deciding how every tenant screens, while a label typed afresh by each reviewer could not be filtered or counted, and "who is cleared for Tier 1" is the question the feature is for. It is the shape `volunteer_role_types` already has, and like that catalog it ships **empty on every tenant**: what the levels are is an organization decision.

`expires_on` is nullable and **display only**. It is rendered beside the outcome and marked expired once past, against the tenant's own day rather than the viewer's; nothing reminds anyone, nothing blocks a role and no ops-inbox item reads it. A recheck _schedule_ is tenant policy and lives in #1320 — only the column is a platform decision.

Screening answers to **`volunteer_screening`, its own resource, never OR'd with `volunteers`** — [`docs/permissions.md`](../permissions.md) option 3, the `event_incidents` and `constituent_claims` precedent. It costs nobody access today, since `volunteers:manage` is admin-only and so is this, but it keeps a later widening of `volunteers:manage` from silently handing out screening data. Because the resource is new, `/portal/volunteers` now guards `volunteers:view` **or** `volunteer_screening:view` with each page re-checking its own — the two-gate shape `/portal/finance` has carried since #903 — so a safeguarding lead can hold screening and nothing else. Both tables are audited with nothing redacted (there is no prose to redact), and `person_screenings` carries a retention clock on Administration → Data Retention, proposed at three years from the end of the clearance and shipping in `dry_run` like every rule before it.

Volunteers (role types, hours logging) is fully implemented, not a placeholder.

## 6. Data model — Volunteers

**Implemented** (issues #49/#50) — see §5.17.

- `volunteer_role_types`: catalog of role-type definitions (e.g. Ride Buddy, Event Setup, Basecamp Staffing) — named to avoid colliding with the existing RBAC `roles` table in "Identity and access" above, which is a different concept (portal permissions, not volunteer job types). Currently `name`/`description` only.
- `volunteer_hours`: `person_id` (→ `people`), optional `event_id`, date, hours, `volunteer_role_type_id`, the user who logged the entry, and `updated_at`/`updated_by`. Since 20260904010000 this is the single hours ledger behind both entry points — Volunteers > Participation and the event editor's Volunteers tab (an event-scoped view of the same rows) — with dual permission gates: `volunteers` for the ledger as a whole, `event_volunteer_hours` for rows where `event_id is not null`. Rows logged from the event tab carry no `volunteer_role_type_id`; that tab has no role picker.
- `volunteer_role_types.is_public` + `public_volunteer_role_types`: **implemented** (issue #60) — a public-facing flag on `volunteer_role_types` and a curated view (`id`, `name`, `description`) granted to `anon`, backing `/get-involved/volunteer`.
- `volunteer_hour_submissions`: **implemented** (issue #1165) — hours a volunteer logged for themselves from `/my`, provisional until confirmed: `person_id` (composite tenant foreign key to `people`), optional `event_id` and `volunteer_role_type_id`, `hours` (capped at 24), `logged_date`, `notes`, `status` (pending/confirmed/declined), `volunteer_hours_id` (the ledger row it became, null until then and null forever for a decline), `created_by` (the volunteer, which is the record that they entered it) and the reviewer triple. Audited, with the volunteer's and the reviewer's prose redacted. A partial unique index keeps one pending submission per person per day per event. Reads are `volunteers:view` for staff and the caller's own row on the public host; both writes are `security definer` functions, so a constituent holds no insert grant on it at all.
- `volunteer_screening_tiers`: **implemented** (issue #1360) — the screening levels one tenant recognises, in its own words: `name` (unique per tenant), `description`, `sort_order`, `is_active` and the audit quartet. Ships empty on every tenant, like `volunteer_role_types`. Retiring a level is `is_active = false` rather than a delete, because `person_screenings` references it `on delete restrict` — the level's name _is_ the outcome, so a clearance whose level had been deleted would say "cleared for nothing".
- `person_screenings`: **implemented** (issue #1360) — one recorded outcome: `person_id` and `tier_id` (both composite tenant foreign keys), `cleared_on`, nullable `expires_on`, and `created_by`/`created_at` as the record of who decided and when. Unique on `(tenant_id, person_id, tier_id, cleared_on)`, which catches a double-tapped submit and nothing else. No status column, no note, no reference and no result — see §5.17 for why each absence is load bearing. Gated on `volunteer_screening` rather than `volunteers` on all four verbs, audited with an empty `redacted_columns`, and swept by the `person_screenings` retention rule measured from `coalesce(expires_on, cleared_on)`.
- `volunteer_applications`: **implemented** (issue #161) — public intake, separate from the role-type catalog above: `person_id` (→ `people`), `name`, `email`, `phone`, free-text `role_interest`, `availability`, `status` (new/being reviewed/contacted/placed/declined/closed), submitted via the `security definer` `submit_volunteer_application()` RPC. Also carries `updated_at`/`updated_by` (issue #173, backing the portal triage queue at `/portal/volunteers/applications` — see §5.17) via the same shared `set_updated_at` trigger used elsewhere in the schema.
