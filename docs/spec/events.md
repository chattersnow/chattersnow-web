## 5.2 Public events

The site shall allow visitors to:

- View upcoming events.
- View past events.
- Open an event detail page.
- See date/time, location, and description.
- See sponsors or partners when marked for publication.
- Register when registration is enabled.

Events are presented as a list in the initial release. A calendar view is a possible future enhancement, pending research into a suitable approach; the data model should not preclude it.

**Implemented:** `/events` lists upcoming and past events read live from Supabase (`public_events`) and opens event details in a sheet (with `/events/e/[id]` kept as a direct-link detail page, and `/events/[id]` permanently redirecting there for links shared before the move) showing date/time, location, description, and public sponsors/partners (`public_event_sponsors`, sourced from `event_sponsors`/`people` and limited to sponsors marked `is_public`), plus a public registration form (when `registration_enabled` and within the registration window) backed by `event_registrations` and the `register_for_event()` RPC (see [§6](../technical-spec.md#6-proposed-data-model)). After the response, the registrant receives their own confirmation (#1068, kind `event_registration_confirmation`, which is deliberately not in `NOTIFICATION_KINDS`: they hold no portal account and so no preference row, and only the tenant's org-wide email switch governs it). It restates the event, its window in the event's own timezone with the zone labelled, its place and the party size, links to the public event page on the tenant's own domain, and attaches the event as a `text/calendar` file; it deliberately echoes back neither the phone number nor the notes. Staff are not notified of a new registration -- tracked separately.

**The form waits to be asked for** (#1256). Registration is offered as a single **Register** button, and the fields appear only when it is pressed -- on a phone the sheet's first screen was a form, so the reader was asked to fill something in before the flier, the date line and the description had told them what it was. The button is a disclosure, not a route: the sheet's own URL is worth sharing, "I have started filling in a form" is not, and pushing history for it would put Back between the reader and the listing. It carries `aria-expanded`/`aria-controls`, moves focus to the first field on reveal, and keeps what has been typed if it is collapsed again; the submit is `Complete registration`, deliberately not a second `Register`. Status is _not_ behind it -- somebody already registered, or past the deadline, is told so with no button to press, because that sentence is the answer the button would otherwise raise.

**A signed-in visitor is not asked to retype what the account already holds** (#1257). `loadEventViewer()` distinguishes a session with no approved claim ([§5.23](constituent-accounts.md#523-constituent-accounts)) from a visitor with no session at all: the first still registers down the anonymous path, but its name and email arrive prefilled from `auth.users` -- the verified address, and a display name from the OAuth metadata where the provider gave one -- above a single `Signed in as …` line. Both fields stay editable, and the submission still goes through `register_for_event()`, which matches or mints the `people` row as before; the point is that a retyped address is how a duplicate gets made. Everything on that screen is derivable from the caller's own session and nothing from the directory: a form that changed according to whether the address matched a `people` row would answer "do you have a record of this person?" for anybody who can make an account, which is what [§5.23](constituent-accounts.md#523-constituent-accounts)'s silence rule refuses.

An event must support these fields:

- Name
- Description
- Start and end date/time, including timezone
- Location or location description
- Status: draft, published, completed, cancelled, or archived
- Public/private visibility
- Registration enabled/disabled
- Optional capacity
- Optional public registration deadline

Future event capabilities may include registration status, waitlists, and event photos.

## 5.5 Event management

Authorized users shall be able to create and manage events, including:

- Name
- Location
- Date and time, including timezone
- Sponsors
- Associated expenses
- Giveaway sales
- Public/private visibility and publication status

The event record should support a public/private boundary so internal planning details do not become public accidentally. Registration, volunteers, and inventory distributions may be added as later capabilities. Attendance is implemented as a simple event-level headcount (`attendance_count`, `attendance_notes`) rather than per-attendee records — a deliberate product decision, not a placeholder.

**Also implemented, on `events` itself:** an event lead (`event_lead_id` → `auth.users`), capacity, and an after-phase report workflow (`report_status`: not_started/in_progress/submitted, `report_summary`, `lessons_learned`, `feedback_notes`, `content_notes`, `report_submitted_at`), surfaced on the event editor's Report tab. `location` is the single place field: a `venue` column described the same thing a second time — the public pages already rendered `venue ?? location` — and was merged into it. There is no event-type field either: the programs an event counts toward _are_ its categorisation, so `event_type` and its curated `src/lib/event-types.ts` list were both removed. **An event can belong to any number of programs**, through the `event_programs` join table rather than a single `program_id` — one access day can serve two programs, and the Program Impact Report counts it in full for each, since both genuinely ran it.

**Also implemented, as separate per-event tables/tabs on the event editor:** planning-phase logistics (`event_logistics` — meeting point, gear requirements, transportation, food, supplies, emergency contact, notes; one row per event) and a during-phase incident log (`event_incidents` — description, severity: minor/moderate/serious, people involved, occurred-at, reporting user; restricted to `admin`/`event_coordinator` since incident detail is more sensitive than the rest of the events cluster). This event-scoped incident log satisfies the operational need described in [§16.1](addenda.md#161-incident--problem-documentation), though it is narrower than that addendum's proposed cross-cutting `incident_reports` table (no inventory-item linkage, no open/resolved workflow) — see [§16.1](addenda.md#161-incident--problem-documentation) for the remaining gap.

### Registering as yourself

**Implemented** (issue #1165, epic #1160). A visitor with an account that is linked to a directory record gets a different registration form on a public event page: prefilled, and attached to the `people` row they already have. `register_myself_for_event()` takes no name and no email, so unlike the anonymous `register_for_event()` it never calls `resolve_or_create_person_by_email()` — which removes the largest single source of duplicate `people` rows. Everything else is deliberately identical, because it is a property of the event rather than of who is asking: the same `(route, ip)` rate limit, the same public/published/`registration_enabled`/deadline checks, the same `for update` lock on the event row before seats are counted (so the two registration paths queue behind each other rather than each overrunning a capacity the other has filled), and the same discount-code assignment. `event_registrations_event_person_key` is what makes a second attempt `ALREADY_REGISTERED`.

**The participant agreement is kept on file** (issue #1401). Where the tenant has a waiver in force, the first acceptance on this path is written to `person_waiver_acceptances` (tenant, person, version, `accepted_at`) as well as to the registration. On the next event, `my_waiver_on_file()` returns that acceptance while its version is still the one in force, and the form replaces the agreement and its box with one line — "Participant agreement v3 · accepted Oct 4, 2026 · view", linking `/waiver?version=3`. The RPC then accepts an unticked submission and copies the on-file version and `accepted_at` onto the new registration, so `waiver_version`/`waiver_accepted_at` mean what they always did. Publishing a new version makes the file stale at once and the full block returns; a submission made against a summary the republish overtook is refused as `WAIVER_CHANGED`, not `WAIVER_REQUIRED`, since there was no box to tick. **Linked accounts only:** `register_for_event()` never writes the file, because its person is an email match and an email match is not identity. No expiry yet — a per-tenant period (per season, as Smartwaiver and WaiverForever offer) would be a filter on `accepted_at` in `waiver_on_file()`.

Party size, phone, pronouns, Instagram handle and a note may be corrected on the form; they land on the registration and are **not** written back to `people` (see [§5.9](people.md#acting-from-your-account)). Somebody already registered is shown that, rather than a second form. There is no cancel: `event_registrations` has no cancelled state and no delete path anywhere in the application, so the only thing a button could do is destroy the row, and with it the attendance figure and any assigned code.

### Have you been before?

**Implemented** (issue #1259). Both registration forms ask one more question — "Have you been to one of our events before?" — and store the answer on the registration as `event_registrations.attended_before`. An organizer knows who to look after on the day, and a claim reviewer ([§5.23](constituent-accounts.md)) gets the one piece of evidence that helps most when an email matches nobody: "I came to the November swap" is a record to go and look for.

Three things make it work, and each one is a rule rather than an implementation detail.

**It is asked of everyone, identically.** A question that appeared only for addresses matching no `people` row would tell the reader whether the organization has a record of them, which is precisely the enumeration answer the claim flow refuses to give. The cost of asking somebody we already know is one redundant question; the cost of asking selectively is an oracle. `register_for_event()` branches on nothing about the address, and the field renders the same for a visitor with no session, an account whose claim is unapproved, and a linked constituent. It is a field on the form rather than a step after the write, because a step after the write is one that can be abandoned.

**Unanswered is a third state.** The column is nullable, null means the question was not answered, and nothing anywhere may read that as "no". Every row that predates this ticket is null, so a count that folded them into the first-timers would be wrong by the whole population. `countSelfReportedFirstTimers()` counts `=== false`, and the portal shows the column only once somebody has answered.

**It never replaces the derived figure.** First-time versus returning is computed from check-ins — `computeFirstTimeParticipants()`, `get_event_impact_derived_data`, the People segment counts — and those are unchanged and remain the only source for anything that reaches an impact report. A self-reported answer and an attendance record are different facts, and the portal shows them side by side with the wording carrying the difference ("1 first-time" against "1 said it would be their first"). The register-as-yourself form asks it too rather than deriving it from `my_event_history()`: the ledger only knows the events this tenant ran on this platform, and seeding the one self-reported column from the derived one would make it a second copy of the thing it exists to sit beside.

It appears in the portal on the event's registrant list (a column and a count) and on the person record's Event registrations card, worded as a quotation. It appears nowhere public.

### Is anyone in the party under 18?

**Implemented** (issue #685). Both registration forms ask one more question — "Is anyone in your party under 18?" — and a yes collects the accompanying adult's name and mobile number and an emergency contact. `/code-of-conduct` and `/terms` have said since they were written that a minor takes part only with a parent or guardian; nothing in the product knew whether one was coming, so a party of four could be one adult and three children and the first anyone found out was on the day.

**The platform ships the mechanism and none of the rule.** What an organization _requires_ — who must accompany, whether that adult registers too and counts in the party size, whether there is a minimum age at all — is that organization's claim, so it is the `events.minor_accompaniment` content slot, blank until somebody writes it, exactly like `get_involved.volunteer_screening` ([§5.11](volunteers.md)). A tenant that has adopted nothing shows nothing, promises nothing, and still gets the flag on its registrant list. What the form _asks for_, and that it never asks a date of birth or an age, is a fact about this software and renders on every tenant from the component. That split is `docs/legal-basis.md` rule 2, and `minors.test.ts` checks the second half against the schema.

**Required on the forms, three-state in the column.** Unlike "have you been before?", which has a real "rather not say", this question is required: the accompanying-adult block, the organizer's flag and the organization's own rule all hang off the answer, and an unanswered one leaves the gap the field exists to close. `event_registrations.party_includes_minor` stays nullable all the same, and null means **nobody was asked** — every row written before this shipped, every walk-in and staff-added registrant, and every caller of the public API, whose published contract predates the question. Nothing may read null as "no". The RPCs enforce only the conditional: a `true` that arrives without all four contacts raises `MINOR_CONTACTS_REQUIRED`.

**Asking is a per-tenant setting** (issue #1416). The question is asked unless an organization turns it off from the **Registration** button on the portal's Events page (`events: manage`). The setting is `registration.asks_about_minors` in `app_settings`, and a missing row means on, so every tenant, new tenants included, asks unless it decides not to. Chatter Snow has it off. With it off, neither form renders the question or the contacts, and both registration RPCs ignore an answer or contacts that arrive anyway (the public API included) and store null, the column's "nobody was asked". Nothing is dropped: the columns, `events.minor_accompaniment`, `MINOR_CONTACTS_REQUIRED` and the retention rule stay, and contacts stored before the setting was turned off are still cleared on the usual schedule. The public form reads the setting through `public_registration_settings`.

**Adults only (18+) is a per-event setting** (issue #1417). `events.adults_only`, off by default, is a switch on the event's Planning tab. On, the public site shows an **18+** badge on the event card, the detail page and the sheet header; step 2 of registration asks a required, unticked "Everyone in my party is 18 or over" instead of the under-18 question, which an 18+ event never asks whatever the tenant setting says; and both registration RPCs refuse a registration without `p_adults_only_confirmed = true` (`ADULTS_ONLY_CONFIRMATION_REQUIRED`, shown on step 2), discard any under-18 answer, and record the confirmation as `event_registrations.adults_only_confirmed_at`, shown in registrant detail. Off, the confirmation is ignored and nothing about age is asked beyond the tenant setting. The public API exposes `adults_only` on events and takes `adults_only_confirmed` on a registration.

**Nothing is accepted here.** Per [§5.22](../technical-spec.md), these paragraphs are notice: no checkbox, no stored pointer to a version. The one box on the registration form carrying a real choice is the participant agreement's, and a second box nobody can decline would dilute it. The single thing a registration submission now carries is the photo agreement below (#1376), which is a claim the organization makes in its own words and is deliberately not called consent — it does not reach this question, and nothing about a party including a minor is agreed to by submitting.

**The flag and the contacts are gated differently, and the contacts are gated by privilege.** Any holder of `events: view` sees that a party includes someone under 18 — the door shift has to know before the day, not at it. The four contacts are readable only at `events: manage`, and not by convention: 20260922040000 revokes those columns from `authenticated` on `event_registrations` and serves them through `event_registration_minor_contacts`, a security-definer view carrying its own tenant isolation and its own permission check. The rider block beside it is gated in TypeScript alone, which was an acceptable cost for a riding preference and is not one for a guardian's mobile number. The four are cleared by the retention purge with the other personal fields; the flag survives beside `party_size`.

It appears nowhere public, and deliberately not on the person record: the answer describes one party at one event, and a standing "brought a minor" marker on somebody's directory row is a different and more sensitive claim than the one that was collected.

### Photos and video

**Implemented** (issues #599, #1376). #599 asked a question at registration — the organization's own paragraphs above an unticked box — and #1376 reversed it. **Registering for an event is itself the agreement to being photographed, and the remedy is removal**: any photo can be taken down on request, at any time. There is no box, and a decline box as an opt-out was declined too. The decision is recorded in [`docs/legal-basis.md`](../legal-basis.md), "Registering carries the photo agreement", which partially supersedes #1318 for this one form.

**The word "consent" is gone from every surface a human reads, and the column names stay.** Agreement implied by submitting a form is not an unambiguous affirmative act, so calling it consent in a privacy policy would misstate the lawful basis; the honest framing is notice plus a standing right to object. Renaming `photo_consent` to `photo_objection` would mean retyping both registration RPCs, the column grant list, a published API field, the generated types and every test, for a name — so `20260923020000` is a comments-only migration that flips what the columns mean and touches no row.

**The mechanism is the platform's and the implication is the organization's, and here blank removes the notice rather than softening it.** `events.photo_consent` is empty on every tenant by default, and empty means no heading, no notice, no paragraphs and a registration form byte-identical to the one before #599 — which is where almost every tenant stays. That is [`docs/legal-basis.md`](../legal-basis.md) rule 2 at its sharpest and #1376 sharpened it again: what an organization does with a photo of somebody's face is off-platform, and since these paragraphs are what makes registering carry the agreement, a default here would be the platform implying an agreement on a tenant's behalf. The platform adds no sentence of its own beneath them: how to object is the organization's to say in its paragraphs.

**Three states, and only one has an operational job.** `null` means **no objection on record** — agreement implied by registering — and is the resting state of every registration this platform takes, along with every row that predates #599, every walk-in, every staff-added registrant and every API caller that did not ask. `false` means **objected: do not photograph**, and it is what somebody checks before pointing a camera. `true` means the objection was withdrawn, or that an API caller that genuinely asked recorded an explicit confirmation. Nothing may read `null` as an objection, and **nothing writes `true` at registration** — a form with no affirmative control cannot produce an affirmative record. **No row was backfilled and none needed to be**: `false` means exactly what it meant under #599, and `null` meant "nothing to act on" under both models.

**A snapshot rather than a version pointer**, which is #1319's test rather than #686's: the version-table shape earns its cost only where the text must be citable from outside the row that holds it, and a content slot has no version table and no permalink. `resolved_photo_consent()` reads the paragraphs from `site_content` itself and joins them, so the words are never supplied by whoever posts the form — the invariant `artwork_submissions.consented_terms` carries. Since #1376 `photo_consent_text` is a copy of what somebody was **told** when they objected rather than of a question they were asked, and nothing writes it at registration time.

**Not a fifth legal document.** #686 made the waiver one because a release of legal rights is one: sections, a version history, an address somebody can be sent to. This is a notice and a record, so there is no `/photo-consent` route, no registry entry, no `legal_publication.*` row and no `legal_surface.*` key — the last because a surface key meaning "this tenant publishes a photo notice" would tell every tenant with its own published documents that it had drifted.

**No guardian branch.** #599 reworded the box where the party included someone under 18, so the registering adult answered in a parent-or-guardian capacity. With no box there is nothing to reword, and a platform-written sentence saying an adult's submission binds the under-18s in their party would be a guardianship claim the platform is in no position to make. A tenant's own paragraphs cover minors if it wants them covered.

**Objecting: three routes, one of them self-service.** Telling any organizer at the event, emailing, or — only for somebody who has claimed an account (see [§5.23](constituent-accounts.md)) — `set_my_photo_consent()` from `/my/registration/[id]`. That last resolves through `my_constituent_person_id('events')` and most registrants have never claimed an account, which is why the privacy policy names the organizer and the email first and qualifies the third rather than promising it. `my_photo_consent()`'s `asked` flag is computed from the tenant's slot alone, with no reference to the row's own columns, so the control appears for every registrant of a tenant that publishes a notice — including the overwhelming majority whose three columns are null. The RPC refuses a `null` write with `PHOTO_CONSENT_REQUIRED`, because letting somebody write `null` back would erase the record of having objected, and refuses with `PHOTO_CONSENT_UNAVAILABLE` where the organization publishes no notice, rather than silently clearing a row an organizer acts on.

**Staff see it where it is needed, at `events: view`.** A `No photos` badge beside the name on the event's registrant list, rendering only for an objection, and all three states in the registrant sheet with the snapshot behind a disclosure. The Happening Now check-in sheet renders the same list, so the badge is at the door with no second copy. **That badge is why #1376 kept the columns at all**: dropping them would have deleted the list the door shift checks, and "photos can be deleted" is a remedy after the fact rather than a list of people who asked not to be photographed.

**Retention clears all three, which is the opposite call from the waiver's on the same row** — see `docs/legal-basis.md`, where the rationale is restated against the new meanings: an instruction about a face nobody can identify is no more useful than a permission was.

### Registration options

**One optional single-choice question per event** (issue #1407) — a prompt and an ordered list of up to ten options, such as Chatter Snow's "I'll use my own / I need a ticket / I need a ticket and gear", or "bring my own mat / need a mat" for anyone else. The platform knows nothing about what an option means. An event with no options asks nothing and behaves exactly as before.

**Answered per person as counts.** Where an event has options, both registration forms, the public API and `register_for_event()`/`register_myself_for_event()` (`p_option_counts`, an object of option id → count) require counts that add up to `party_size`; party members are not named. Refusals are `EVENT_OPTIONS_REQUIRED`, `EVENT_OPTIONS_MISMATCH` and `EVENT_OPTIONS_INVALID`, and a refused answer rolls the registration back with it.

**An option may be capped** (10 sponsor tickets, 6 gear sets). A cap is enforced under the same `for update` lock on the event row as `events.capacity`, taken before the registration insert, so concurrent registrations cannot oversubscribe it; a full option is refused with `EVENT_OPTION_FULL` and shown as full on the form (the public view exposes `is_full`, never the counts), while the others stay open. Only an increase is refused, so a registrant keeping what they hold is never turned away. **Staff are not capped**: the portal's add-registrant and walk-in dialogs record counts through `set_registrant_option_counts()`, optional and uncapped, as `events.capacity` is not enforced on them either.

**Set up on the event's Planning tab** beside capacity, through `save_event_registration_options()` (add, rename, reorder, remove, cap). A tenant's defaults in `app_settings` key `events.registration_option_defaults` (`{"prompt": …, "options": [{"label": …, "cap": …}]}`) are copied onto every new event by an insert trigger and are then the event's own. Chatter Snow's are seeded (`20260923110000`).

**Answers keep their words.** Each count row copies the option's label as shown; renaming an option leaves old answers alone, and removing one keeps its counts with a null `option_id`.

**Where they show:** a column and per-option totals against caps on the registrants tab, the registrant sheet, the confirmation email ("Your choices"), `GET /events/{event}` (`registration_options`), and `/my/registration/[id]`, where a linked registrant can change their answer through `set_my_registration_option_counts()` while registration is open — held to the same sum and caps.

Out of scope: gear sizing (the rider profile add-on, #1408), named party members, payment.

### Cancelling a registration

**Cancelled, not deleted** (issue #1418). `event_registrations` carries `cancelled_at`, `cancelled_by`, `cancellation_reason` (`not_attending | mistake | duplicate | other`) and an optional staff `cancellation_note`. The row stays, so history, "been before" and claim-from-registration keep reading it.

**What a cancellation frees.** Both registration RPCs sum only active rows against `events.capacity`, and `apply_registration_option_counts()`, `public_event_registration_options.is_full` and `my_registration_option_counts()` sum only active rows against an option's cap; the counts themselves are kept. A discount code reserved for the registration is released back to the pool, unless it was already sent. The one-per-person and one-per-email unique indexes cover active rows only, so somebody who cancelled can register again. A check constraint keeps a registration from being both cancelled and checked in.

**Who cancels.** Staff with `events: manage` cancel from a row action on the Registrants tab, with a reason and a note (`cancel_event_registration()`), and optionally email the registrant. Cancelled rows sit behind **Show cancelled**, where staff can **Restore** them (`restore_event_registration()`). A restore is refused if the seats (`EVENT_AT_CAPACITY`) or an option's cap (`EVENT_OPTION_FULL`) have been taken since, or if the person has registered again (`ALREADY_REGISTERED`). A linked registrant cancels their own registration with **I can't make it** on `/my` or on the event page, until the event starts (`cancel_my_event_registration()`, `EVENT_ALREADY_STARTED` after). That records the reason as `not_attending` and sends them a "your registration was cancelled" email, which is recorded in the registration's message history.

**Where it drops out.** Cancelled rows are excluded from check-in, announcements, one-to-one registrant messages and resent confirmations, the tab's counts, option totals, the portal home and calendar-preview figures, the "still to check in" attention item, and the impact RPCs' registration lists. `/my` and the person record's attendee card list them marked **Cancelled**.

Hard delete is unchanged: the `event_registrations delete` policy (`events: manage`) stays, and nothing in the application uses it. Out of scope: waitlist promotion and refunds.

### Rider profile (add-on module)

The "Do you ski or snowboard?" questions on registration's second step, its door-side counterpart on the registrants tab, the "What you ride" group on `/my/details`, the rider fields on the person record and form, and the Impact "Beginner participants" figure are one add-on, the `rider_profile` module (#1408). It is off by default on every plan and on only for Chatter Snow; the generic replacement is designed in #1409.

**One gate per audience.** In the portal the module's resource, `rider_profiles`, is asked for beside each screen's own permission (the registrants list still needs `events: manage`), so `has_permission()` turns every rider surface off with the module. On the public site, `register_for_event()` and `register_myself_for_event()` ignore the four riding arguments without the module, and `save_registrant_rider_profile()` (called now only by `POST /rider-profile` in the public API) refuses with `SECTION_UNAVAILABLE`, a 404 there. `set_my_contact_details()` ignores the four rider arguments without the module and leaves the stored answers alone — off is frozen, never cleared.

**Asked on step 2, stored on the person** (#1415). With the module on, both registration forms title their second step "Your riding" and ask the discipline (required), the level for each discipline ridden, and the home mountain; the post-registration follow-up (#564) is gone. Both RPCs validate the answers as `save_registrant_rider_profile()` did and write them to `people` in the registration's own transaction through `apply_registration_rider_profile()`, so a refusal rolls the registration back. A null discipline writes nothing, which is what the public API's register call sends. The check-in snapshots (`*_at_event`) are unchanged. Only the register-as-yourself form prefills the answers, from the caller's own record; the anonymous form never does, even for a signed-in account, because the only record it could read from is the one a typed email matches.

**The mountain list is the tenant's.** `app_settings` key `rider_profile.preferred_mountains` (a JSON array of names, in picker order), edited from the **Mountains** button on the Events page (`rider_profiles: manage`, through `set_rider_profile_mountains()`), read by the public step through `public_rider_profile_settings` and by the portal through `rider_profile_mountains()`. "Other" is never stored in the list: both pickers add it with a free-text box, and what lands on `people.preferred_mountain` is the chosen or typed name, so editing the list never rewrites an answer. Chatter Snow's list is seeded (`20260923120000`).

### Sponsor and partner selection

Event sponsors/partners are people or organizations that already live in the shared `people` directory (the same table backing donors and volunteers, see [§6](../technical-spec.md#6-proposed-data-model)) rather than free text typed per event. Managing an event's sponsors shall work as follows:

1. The event editor's Sponsors tab provides a type-ahead search (matching on name and email) over `people`. Staff pick an existing person/organization from the results to link them to the event.
2. If no existing record matches, the same control lets staff create a new `people` record inline (name required; email, phone, and notes optional) and link it to the event in one step, without leaving the event editor.
3. Linking a person makes them a sponsor in the People directory (`/portal/people`) going forward, and their other roles are unaffected. **Implemented** by the derived role model described in [§5.9](people.md#59-people-directory) rather than by the sponsor-linking code: the `event_sponsors` row _is_ what makes them a sponsor, and unlinking their last sponsorship stops it. While the roles were stored flags each caller had to remember to set, linking an _existing_ person set nothing and `/portal/sponsors` was missing sponsors (issue #620).
4. Per-event sponsorship details — support type (cash, in-kind, both, other), in-kind description, contribution value, public visibility, and notes — are stored on the event-sponsor link, not on the person record, since the same sponsor can support different events differently.
5. A person may be linked to a given event only once; re-selecting an already-linked person edits the existing link rather than creating a duplicate.
6. An in-kind sponsorship is mirrored into `donations` + **one `inventory_items` row per item** (issue #1005) so the goods are tracked and valued like any other donation. A sponsor hands over several distinct things at once — a board, goggles, five tees, four lift tickets — and each has its own fate, so the Sponsors tab records a list: description, value and destination per row. The items _are_ the inventory rows under `event_sponsors.donation_id`; there is no sponsor-items table, which is what makes the rest of the app work on them unchanged. Each appears separately in the Giveaway tab's prize-source picker (`list_available_giveaway_sources` already lists every inventory item on the event's donations), so items can be combined across prizes and buckets however the draw is run.

   Each item's `intended_use` defaults to `giveaway`: sponsor contributions are usually vouchers, gift cards or lift tickets destined for an event giveaway, not gear for the community to take home, so by default they reach neither the public gear catalog, the public request flow, nor the rider distribution picker. An item the staffer sends to `gear_library` does reach all three — that is the point of the per-item destination, and it is how a sponsor's gear gets onto the public site. Items can still be reclassified afterwards from Inventory › Items.

   Removing an item is refused while a giveaway prize names it (`giveaway_prizes.source_inventory_item_id` is `on delete set null`, so an unguarded delete would empty the prize in place) or while it carries movement history beyond its intake. The tab disables that row's remove control rather than letting the staffer hit the error.

   `in_kind_description` is derived from the item descriptions rather than typed, so the two can never disagree, and `contribution_value` stays a manual figure that defaults to the items total. `'both'` mirrors its in-kind half on the same terms; its cash half remains unmirrored, since one `contribution_value` cannot be split into cash and goods without inventing a number.

**Where a public sponsorship shows** (issue #914): on its event's detail page, and on the tenant's `/support/sponsorship` page, through the `public_sponsor_wall` view -- the same join as `public_event_sponsors` with the event dropped and one row per person, so a logo no longer leaves the public site when its event ages out. **The wall has two arms and two opt-ins** (#1024). The first is a sponsorship marked `is_public` on a published public event, above. The second exists for a sponsor who supports the organization rather than an event -- an annual partner, a business funding a program -- who has no sponsorship to mark and could previously reach the public site only behind a fake event: a `person_role_tags` sponsor assertion carrying its own `is_public`, ticked on the person form. That arm is **organizations only**, on the same grounds as the logo and website it publishes: the wall shows a mark, and an individual with no logo would be published to a public page as their own name. Both arms stay derived rather than curated -- neither writes a second copy of a sponsor's name, logo or website, which always come from the one `people` row -- and a sponsor who is both event-credited and hand-published appears exactly once. The heading and intro above the logos are tenant-owned copy (`support.sponsor_wall_heading`, `support.sponsor_wall_intro`), and a tenant with no public sponsors renders no section at all.

## 6. Data model — Public and events

- `pages` or repository content: approved public content
- `events`
- `event_sponsors`: links an event to a `people` record via `person_id` (one row per event/person pair), plus per-event sponsorship details — support type, in-kind description, contribution value, public visibility, notes. Sponsor/partner name and contact info are not duplicated here; they live on the linked `people` row. `donation_id` and `monetary_donation_id` point at the records the sponsorship mirrors (§5.5); the in-kind items are the `inventory_items` rows under that donation, any number of them, each with its own value and `intended_use` (#1005). A `inventory_item_id` column named a single mirrored item until #1005 dropped it — it could only ever name one of several, and it is derivable from `donation_id`.
- `event_volunteers`: links an event to a `people` record via `person_id`, with an optional free-text `role` and notes; a lightweight, event-scoped sign-up list, separate from the `volunteer_role_types`/`volunteer_hours` catalog in "Volunteers" below. Optional `shift_id` (issue #70) assigns the volunteer to a time-bounded `event_shifts` row.
- `event_logistics`: **implemented** — one row per event (`event_id` PK/FK): meeting point, gear requirements, transportation, food, supplies, emergency contact name/phone, notes. A separate table rather than more `events` columns, matching the `event_sponsors`/`event_expenses` per-tab pattern.
- `event_incidents`: **implemented** — see §5.5/[§16.1](addenda.md#161-incident--problem-documentation): `event_id`, `occurred_at`, `description`, `severity` (minor/moderate/serious), `people_involved`, `reported_by`. Restricted to `admin`/`event_coordinator`.
- `event_shifts`: **implemented** (issue #70) — time-bounded shifts within an event (e.g. basecamp AM/PM on a multi-day trip): `event_id`, `label`, `starts_at`/`ends_at`, optional `target_headcount`, notes. Scoped to `event_volunteers`; staff-side shift assignment is still a follow-up now that `event_staff` ([§5.9](people.md#59-people-directory)) exists. Managed from the event editor's Volunteers tab, gated by the `events` resource.
- `event_volunteer_hours`: **retired** (20260904010000) — was a lightweight, event-scoped hours log running in parallel with the org-wide `volunteer_hours` table under "Volunteers" below. The split was a silent reporting bug, not just redundancy: the [§5.15](programs.md#515-impact-tracking-and-reporting) rollup, Volunteers > Participation, and the person profile's Volunteer activity card all read `volunteer_hours` only, so hours logged from the event editor's Volunteers tab appeared on that tab and nowhere else. Its rows were backfilled into `volunteer_hours` (id-preserving, `volunteer_role_type_id` null) and the table dropped. The **resource key** `event_volunteer_hours` survives as the event-scoped permission gate — admin/event_coordinator manage, finance view, board none, volunteer view — OR'd into `volunteer_hours`' RLS wherever `event_id is not null`, so the event tab's access is unchanged and the org-wide ledger is not widened.
- `event_staff`: **implemented** (issue #626) — mirrors `event_volunteers` (`event_id`, `person_id`, optional role/title, notes, unique per event/person pair), gated on the same `events` resource, and is itself what derives the staff role ([§5.9](people.md#59-people-directory)). Managed from the event editor's Staff tab.
- `event_registrations`: **implemented** — public registration for an event (name, email, phone, party size, notes), submitted via the anon-callable `register_for_event()` RPC (validates the event is public/published, registration is open, and capacity). Links to a `people` record via `person_id`, resolved-or-created by normalized email inside the RPC (`resolve_or_create_person_by_email()`, since there's no signed-in user to drive a `PersonPicker`); existing rows were backfilled by matching `people.email` where possible. `create_donation_with_items` uses the same helper to resolve an existing `people` row by email instead of always inserting a duplicate. `checked_in_at`: explicit per-registrant check-in (set by staff from the portal, not derived from `events.attendance_count`/`attendance_notes`, which remain a separate manual estimate — see [§5.9](people.md#59-people-directory)-adjacent event-day tooling). A walk-in who never pre-registered gets their own `event_registrations` row, created at check-in time via `PersonPicker`, rather than a separate table. `attended_before`: **implemented** (issue #1259) — nullable boolean, self-reported by the registrant on either form, null meaning unanswered and never "no". Deliberately stored beside the check-in-derived first-time/recurring figures and never merged into them; staff-added registrants and walk-ins are null, because nobody asked them. See "Have you been before?" above. `party_includes_minor`: **implemented** (issue #685) — nullable boolean, required on both public forms and null everywhere else (older rows, walk-ins, public API callers), null meaning nobody was asked and never "no". A true carries `accompanying_adult_name`, `accompanying_adult_phone`, `emergency_contact_name` and `emergency_contact_phone`, which a one-directional check constraint permits only alongside it — one-directional so the retention purge can null them while the flag stands. Those four are revoked from `authenticated` on the table and reachable only through the `event_registration_minor_contacts` security-definer view at `events: manage`. See "Is anyone in the party under 18?" above. `photo_consent`, `photo_consent_at`, `photo_consent_text`: **implemented** (issues #599, #1376) — nullable boolean plus a timestamp and a snapshot of the organization's `events.photo_consent` paragraphs, all three written together by `resolved_photo_consent()` from the tenant's own row and never from the client. Since #1376 they hold an **objection** rather than a consent: null means **no objection on record** and is the resting state of every registration this platform takes, **false means objected — do not photograph** and is the state an organizer acts on, and true means withdrawn or explicitly confirmed by an API caller. An objection never refuses the registration, nothing writes true at registration, and **no row was backfilled** — false meant the same thing before, and null meant "nothing to act on" under both models. The names are kept deliberately; `20260923020000` flips their meaning in `comment on` statements alone. A snapshot rather than a version pointer (#1319's shape, not #686's) because a content slot has no version table and no permalink. Readable at `events: view`, changeable by a registrant who has claimed an account through `set_my_photo_consent()`, and cleared by the retention purge with the name — the opposite of the waiver pair beside it. See "Photos and video" above. `cancelled_at`, `cancelled_by`, `cancellation_reason`, `cancellation_note`: **implemented** (issue #1418) — a cancelled registration keeps its row but holds no seats, no option counts against a cap and no unsent discount code, and cannot be checked in. The one-per-person and one-per-email unique indexes are partial on `cancelled_at is null`. Written only by `cancel_event_registration()`, `restore_event_registration()` and `cancel_my_event_registration()`. See "Cancelling a registration" above.
- `events.registration_options_prompt`, `event_registration_options` (`event_id`, `label`, `sort_order`, `cap` nullable) and `event_registration_option_counts` (`registration_id`, `option_id` nullable, `label` snapshot, `sort_order`, `quantity > 0`): **implemented** (issue #1407). Composite tenant foreign keys; RLS select at `events: view`, no write grants — every write goes through `save_event_registration_options()`, `apply_registration_option_counts()` (internal, behind the two registration RPCs, `set_my_registration_option_counts()` and `set_registrant_option_counts()`) and the tenant-defaults trigger on `events`. The public form reads `public_event_registration_options`. See "Registration options" above.
- `person_waiver_acceptances`: **implemented** (issue #1401) — `(tenant_id, person_id, version)` primary key plus `accepted_at`; one row per participant-agreement version a linked person has accepted. Written only by `register_myself_for_event()` (`on conflict do nothing`, so the first date stands), read only through `waiver_on_file()` and `my_waiver_on_file()`, which answer for the version in force alone. RLS on, no policies, no grants; deleted with the person. See "Registering as yourself" above.
- `discount_codes`: manual tracking of discount codes a partner/vendor issues for an event (code, description, source) and which registrant each was given to (`registration_id` → `event_registrations.id`, single-use via a unique constraint on `registration_id`, plus a unique `(event_id, lower(code))` index). No payment/pricing integration — redemption happens outside chattersnow-web. No automatic assignment at registration time (needs board input; tracked separately).
- `contact_messages`: **implemented** (issue #172) — `name`, `email`, `topic`, `message`, persisted via the `security definer` `submit_contact_message()` RPC (honeypot + rate-limited — see [§7.9](../technical-spec.md#79-rate-limit-public-write-endpoints)). **Implemented — portal triage** (issue #173): a `status` column (new/read/resolved) plus `updated_at`/`updated_by`, gated by the dedicated `communications` resource ([§5.3](access-control.md#53-authentication-and-authorization)) rather than the original `is_admin()`-only `select` policy. Staff review submissions at `/portal/communications`; opening a message auto-marks it read, and new messages are flagged in the notification bell and dashboard. **Implemented — outbound notice** (issue #742): the Server Action schedules an email with `after()` once the RPC commits, so a failed or slow send can never delay or roll back the visitor's submission. It goes to everyone holding `communications:manage` or `administration:manage` in that message's tenant who has opted in at `/portal/account`, and deep-links to the message (`?message=<id>`). The email carries the sender's name, address and topic but never the message body — `run_retention_purge` cannot reach an inbox — and sets `Reply-To` to the sender. **Implemented — replying from the portal** (issue #1204): the message sheet carries a Replies list and a **Reply** action behind `communications:manage`, sending through the same `outbound_messages` primitive as [#1203](inventory.md#54-inventory-and-donation-management). Until then a reply left the platform entirely and the message sat in the queue marked handled with nothing to show for it. This is the one adopting queue whose recipient has **no `people` row** — `contact_messages` carries an address and nothing else, and somebody who wrote in once is not a constituent — so the reply keys on `to_email` with a null `person_id`, which is what that column was made nullable for. The subject defaults to `Re:` plus the writer's own topic and nothing of their message is quoted back: they have their own copy. Replying deliberately does **not** move the message's status — a reply that asks a question is not the matter being handled, and conflating them would make the queue lie.
- `rate_limit_hits`: **implemented** (issue #172) — shared abuse-protection primitive (`route`, `ip_address`, `created_at`) behind `check_rate_limit()`; not exposed to `anon`/`authenticated` directly. See [§7.9](../technical-spec.md#79-rate-limit-public-write-endpoints) for which public RPCs use it and at what thresholds.
