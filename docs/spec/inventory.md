# Inventory and donations — specification

Part of [`docs/technical-spec.md`](../technical-spec.md) — section numbers are
unchanged. This file holds §5.4, §5.7, §5.13, §5.19 and the inventory/donations data model. Technology, system boundaries, security, the
route tree and the key workflows stay in the hub. A plain `§N` below is in this
file; a `§N` that lives in another file is always a link.

**Also relevant:** merchandise stock is `product_variants.stock_on_hand`, deliberately not `inventory_items` — see [§5.22](finance.md#522-sales-point-of-sale). Prize allocation reserves an inventory row and keeps it out of the public catalog — see [§5.8](giveaways.md#58-giveaways). An event sponsor's in-kind contribution is likewise ordinary inventory: one row per item under the sponsorship's donation, each with its own `intended_use`, so a sponsor's items reach the gear catalog, the prize picker or neither on their own terms — see [§5.5](events.md#55-event-management).

## 5.4 Inventory and donation management

### Receive a donation

Authorized users shall be able to:

1. Record the donation and donor information when required.
2. Record one or more donated inventory items.
3. Record each item's description, category, size, gender, condition, face value, photo, and status. The photo is **implemented** (issue #781): a per-item field on the items step takes a picture from the device it's being recorded on, compresses it in the browser (longest edge 1600px, JPEG q0.8, EXIF rotation applied) and uploads it to the `gear-photos` bucket as soon as it's chosen — not on save, since an intake volunteer holds `inventory_intake:manage` and nothing else and could not go back and repair a donation that saved without its photo. Pasting an external link still works, so existing Google Drive URLs are not a regression. The category comes from a controlled, admin-managed two-level vocabulary (`inventory_category_groups` -> `inventory_categories`, issue #667), picked from a grouped select rather than typed; choosing "Other" reveals a free-text detail field.
4. Create an inventory receipt transaction.

Source types should distinguish individual, brand, organization, event, and other sources.

### Update inventory

Authorized users shall be able to update item metadata and status, add photos, and create controlled stock adjustments. Adding a photo later uses the same field as intake, on the inventory item editor (issue #781). Each item has its own page, `/portal/inventory/items/<id>` (#1441), reached from the items list and from a scanned tag: breadcrumbs, the item's details, photo, tag and any hold in cards, and a toolbar of icon actions, each with a tooltip naming it — **Edit** (a sheet, `inventory:manage`), **Generate code** and the numbered-code actions. **Copy tag URL**, **Write NFC tag** and **Print label** sit beside each code in the Tag card instead, since an item can have both a tag code and a numbered code and either can be its QR label and NFC tag. The old `/portal/inventory/items?item=<id>` form, which opened the item in a sheet over the list, redirects there, so links and NFC tags written before the page existed keep working. One photo per item, held as a full URL in `inventory_items.photo_url` — a `inventory_photos` table ([§6](../technical-spec.md#6-proposed-data-model)) is still unbuilt and is what a second photo would need. Inventory status should support at least available, distributed, damaged, lost, retired, and other organization-approved values.

**History.** The item's page ends with a History card (#1442): newest first, every movement the item has had — its type as a badge, the time, the event, the recipient, the gear request, the reason and notes, the quantity when it is more than one, and who recorded it — ending at a **Donated** entry for where it came from: the donor (linked to the donation's page), the event it came in at, the donated date, the route it came in by (the donation form or an event sponsor), notes, and who recorded the intake. The intake's own `received` movement is folded into that entry rather than repeated beside it. It is one read, `inventory_item_history(p_item_id)`, a `security invoker` function, so each table's RLS applies as it would to a plain select: a reader who cannot read `donations` sees that the item was donated, and when, but not by whom — the same rule that decides whether they could open the donation's page. The recorder's name comes from `inventory_actor_name`, a definer helper that answers an `inventory:view` holder about users who recorded something in the tenant's inventory. `audit_log` is not a source (its select is `administration:manage`), so category and condition edits are not shown, and tag assignments wait on #1444.

Corrections must record a reason and actor. Quantity should not be changed through an untraceable direct overwrite when a transaction can express the change.

### Distribute or otherwise remove gear

Inventory changes shall be represented by a stock movement or distribution transaction with:

- Item and quantity
- Movement type: received, distributed, reserved, damaged, lost, retired, corrected, or other
- Date/time
- Reason or notes
- Optional event
- Optional recipient or recipient reference
- User who recorded the transaction

For distribution, the system records who received the gear (`inventory_movements.recipient_person_id`, a nullable FK to `people`), when, at which event (also optional), and who distributed it (`created_by`). Recipient data is protected by the same RLS as the rest of `people`/`inventory_movements` and is not exposed publicly.

**Distributing from an item's page (#1443).** A person with `inventory:manage` can start a handout from the item they are holding: the item page's **Distribute** action is offered while the item can go out (in stock, or held — whether the hold is for this recipient is checked once one is picked). It puts the item on their distribution list and opens the same Record distribution form in scan mode, with the recipient picker (including creating a new person), the date and time, an optional event defaulting to the active event, reason/notes and "Mark item as distributed". More gear joins the list before anything is recorded — by the in-page tag scanner, a keyboard-wedge scanner, a search for items without a label, or an NFC tap on another tag, whose resolver offers "Add to your distribution for _recipient_". The recipient and event are kept on the list, so a tag opened in a new Safari tab adds to the same person's handout. The per-item warnings still apply (already distributed, retired, not gear-library stock, held for someone else). Submitting records one `distributed` movement per piece and clears the list; there is no reopenable batch. While a list is in progress the item page offers "Add to current distribution (_N_ items, for _recipient_)" instead of starting another.

**The handout checkout (#1519).** Every handout recorded from the Record distribution form goes through one server-side list — scanning tags and picking from a list both add to it — and is recorded from a second step, **Check out**, rather than directly:

1. **Tags off.** When the pieces are marked distributed, each one carrying a numbered code is a tick-off line ("Tag CSN-007 removed from _Burton helmet_"), and **Record** stays disabled until every one is ticked. Recording frees the code, so the physical tag has to come off before the item leaves. `record_distribution_draft()` takes the ticked codes and refuses with `TAGS_NOT_REMOVED` if they do not cover every numbered code on the handout.
2. **The recipient acknowledges.** The checkout shows a **one-time QR code for this handout** — a token on the draft, never on an item; an item's QR code and NFC tag still only ever open the staff resolver. The recipient scans it on their own phone and lands on `/acknowledge` on the tenant's public site, which shows their first name, the event, the pieces and the current `gearAsIsSummary()`, and asks them to type their name and tick the same required box as the public gear request. The staff screen polls the draft and turns to "Acknowledged by _typed name_ on their own phone". **Hand them this device** opens the same form full-screen on the staff device instead, recorded as such. The token is 32 random bytes whose SHA-256 alone is stored (outside the select grant, as with #1502); showing the code again mints a new one; it works for two hours, only while the draft is open, once, and never after the recipient changes — a trigger on the draft voids the acknowledgement and the token together when the recipient does. Adding pieces afterwards does not: the acknowledgement covers the handout, and the record lists what was actually recorded. A tenant with no public site (the platform tenant) is offered the staff device only.
3. **Or a reason.** Staff can record without the acknowledgement only by choosing why — left before acknowledging, no phone, declined to wait, or other with a note. Otherwise the RPC refuses with `ACKNOWLEDGEMENT_REQUIRED`. When the recipient has an email address and the organization's email is on, the checkout also offers **Email _name_ a link to acknowledge it afterwards** (ticked by default; the reason the box is missing is shown instead when it cannot be offered). The link is minted by the Server Action, its SHA-256 passed to `record_distribution_draft()` and written in the same transaction as the handout to `distribution_acknowledgement_requests`; the email goes out through `deliverEmail()` once the handout is recorded, and a send that does not go out deletes the link and says so beside the "recorded" message. It opens the shared `/acknowledge` page with the recipient's first name, the event and the pieces recorded, works for 30 days, once, and dies if the recipient is anonymized meanwhile. Following it fills in the acknowledgement on the handout's `distribution_acknowledgements` row — method `emailed_link`, **beside** the reason staff gave, so the history still shows the gear went out without it at the time — and writes it back to any pre-#1367 meetup request the handout fulfilled.
4. **Record.** `record_distribution_draft()` writes one `distribution_acknowledgements` row — the acknowledgement or the reason — and points every movement it records at it.

The pending acknowledgement lives on the draft, and the staffer who owns the draft cannot write it: the columns are outside the draft's insert and update grants, and only the security definer acknowledgement functions set them. `record_distribution_draft()` is security definer for the same reason — nobody inserts into `distribution_acknowledgements` directly — and names the tenant and owner itself. **Meetup requests:** a handout every piece of which is held for the recipient under a gear request that already carries the acknowledgement skips step 2 (`distribution_draft_checkout()` says so). A request that predates #1367 collects it at step 2 and has it written back, with `as_is_method = in_person`, so it needs no emailed link (#1518). A drawn signature is out of scope: a ticked box and a typed name against snapshotted text is what every other acceptance in the product is (#686, #877, #1319).

Available quantity should be derived from valid inventory transactions, subject to an explicit policy for damaged, lost, and retired stock.

### Scannable tags

An item can be identified by scanning something attached to it rather than by typing or searching (issue #1420). Each item gets at most one **asset-tag code**: six characters generated server-side from an alphabet without the confusable `0/O/1/I/L`, unique within the tenant, never the item's uuid and never a SKU (an `inventory_items` row is one piece; `product_variants.sku` names a kind of thing and is unrelated). A printed QR label and an NFC tag both carry the same URL, `https://<portal host>/portal/t/<code>`, so a lost label is replaced by printing the same code again. A manufacturer UPC/EAN is recorded as a separate `barcode` tag and may sit on many items; an NFC chip's own serial is an `nfc` tag and, like a code, identifies one item. A code can be generated before its item exists — a pre-printed blank label — and is bound at intake.

`/portal/t/<code>` resolves the code on the request host's tenant and redirects to the item's page, `/portal/inventory/items/<id>`. Signed out, it goes to the login screen and back. An unknown code, a pre-printed blank, and a reader without `inventory:view` all get the same not-found, so the route never says whether a code exists. The resolver and the in-portal scanners share one lookup (`src/lib/inventory-tags.ts`), which also accepts a bare code or a barcode, and refuses a tag URL on another host.

**Labels.** An item's page (**Print label** beside either code) and the items table's selection both lead to `/portal/inventory/items/labels?items=<id>,…`, which draws each label — a QR of the tag URL, the item's description and size, the code in large type, and optionally a Code128 of the bare code for 1D-only scanners — for a US Letter sheet of 30 (1 × 2⅝ in, Avery 5160) or of 10 (2 × 4 in, Avery 5163), or a 2¼ × 1¼ in label printer, and prints it through the browser's own dialog. `&code=numbered|tag` picks which of the items' codes the labels carry; without it the page uses numbered codes when any of the items has one, and offers the choice as **Code**. A numbered label carries the code alone, like one printed from the pool, since it outlives the item it is on; an item without the chosen kind is listed as such. Two more layouts, **Katasymbol 50 × 80 mm** and **Katasymbol 40 × 30 mm** (one die-cut label at a time on a Katasymbol T50M Pro, #1447; sizes as the stock and the Katasymbol app give them, across the printhead first), are for a printer with no macOS or iOS driver, so the print dialog can't reach it. Each label is drawn the way it runs through the printer, never turned: on the upright 50 × 80 stock the logo, a QR about 36 mm across and the text are stacked; on the wide 40 × 30 stock the QR sits left of the logo and text. The content is centred as one group, and every QR module is a whole number of dots. Each label is drawn in the browser at the printer's 203 dpi and cut to black and white, previewed as exactly those dots, and then either sent straight to the printer over USB (WebHID) or Bluetooth LE (Web Bluetooth) from Chrome or Edge, Chrome on Android, or Bluefy on an iPhone, or saved as PNGs of the label's own size (400 × 640 or 320 × 240, stamped 8 dots/mm), shared to Photos/Files on a phone or zipped on a desktop, to print from the Katasymbol app in any browser. The app lays an image out on whatever label it was started with, so the page says to start one of the same size. A link to the retired `katasymbol-50x30` layout opens the 50 × 80 one. The driver in `src/lib/label-printer/` is a port of the MIT-licensed supvan-cups protocol code and loads only when someone prints; it warns when the loaded stock reports a size other than the layout's. Those layouts carry no 1D barcode, which would be too fine at 8 dots/mm. A sheet can start past labels already used. The symbols are drawn server-side (`bwip-js`), so the page ships no barcode code to the browser. Printing an existing label needs `inventory:view`; an item without a code shows as such, and someone with `inventory:manage` creates its code there with one click, or with **Generate code** on the item's page without leaving it. Opening the page creates nothing.

**Scanning.** The same scanner appears in the distribution modal and in a **Scan a tag** dialog, reached from the items toolbar and from the command palette. It takes a keyboard-wedge scanner through a focused text input (no browser API needed), the camera in the page (the browser's own `BarcodeDetector` where it has one, `@zxing/browser` everywhere else, iOS Safari included), and, in Chrome on Android only, Web NFC (**Tap NFC tag**). Web NFC is hidden everywhere else; an iPhone reads the tag natively and opens its URL in Safari. The Scan a tag dialog opens the item a scan identifies, and asks which item when a manufacturer barcode is on several. An item's page can **Copy tag URL** on every browser, which is the iPhone path: paste it into a free app such as NFC Tools to write the tag. In Chrome on Android it can also **Write NFC tag** (the tag URL) directly.

**Scanned distributions.** The distribution modal has a scan mode. Each scan adds one piece to a list, and a mis-scan comes off with one tap. A scan that matches several items asks which one. An item that cannot go out (already distributed, retired or otherwise unavailable, or not gear-library stock) is named and not added. One submit records every piece as its own `distributed` movement in a single transaction (`record_distribution_draft()`, which calls `record_event_distribution()` per piece), with the date, recipient and notes applied to all of them. If any piece was given out by someone else after it was scanned, nothing is recorded and that piece is marked. The list is kept server-side, one per person per event (plus one for no event), so it survives closing the modal. It is also what lets `/portal/t/<code>`, opened from outside the app (an iPhone NFC tap or a phone camera lands in a new tab), offer **Add to <event> distribution** instead of redirecting. That offer appears only when the reader has a list they touched in the last 12 hours. It renders only after the lookup has found the item, so it reveals nothing the redirect would not. The modal requires a connection; scans are not queued offline.

**Tagging at intake.** A received item is never left untagged: `create_donation_with_items()` gives every item it creates an asset-tag code in the same transaction and returns the codes, in item order, beside the item ids. The donation sheet then stays open on a confirmation that lists each item with its code and offers **Print labels** for exactly those items, at `/portal/inventory/donations/labels?donation=<id>` — under Donations rather than Items because the intake volunteer (`inventory_intake:manage`, no catalog access) is its main reader; the rows come through `inventory_intake_labels()`, which returns only what goes on a label. Each item in the sheet can **Scan label or barcode**, using the same scanner as a handout. A **pre-printed blank label** — a batch made ahead of an intake day from Donations → **Blank labels** (`create_blank_asset_tags()`, at most 150 at a time, printed at `…/labels?codes=<code>,…`) — is bound to the item instead of a new code being generated; a label that is not an unused one of this tenant, or is scanned onto two items, fails the whole donation rather than issuing a different code from the one stuck on the item. A **manufacturer barcode** is stored as a `barcode` tag, and if another item already carries it, the sheet fills in that item's name and category where they are still empty. The form learns what a scan is from `inventory_intake_scan()`, which answers a label's status (blank, assigned or unknown) and, for a barcode, that one item's name and category — nothing else of the catalog. `/portal/t/<code>` on an unused blank offers **Receive a donation with this label** (opening the sheet with it on the first item) to someone who may record a donation, and the same not-found as an unknown code to anyone else. None of this needs `inventory:manage`: the functions are `security definer`, gated on the same `finance:manage` or `inventory_intake:manage` pair as recording the donation.

**Reusable numbered codes (#1444).** Besides its permanent random code, an item can hold a **numbered code**: a slot in a pool that is printed and written once and then moved from item to item, so an NFC tag stuck on a helmet that has been handed out goes on the next piece without being rewritten. A numbered code is `<PREFIX>-<NNN>`, e.g. `CSN-007`: the prefix is three letters set per tenant (`tenants.inventory_tag_prefix`, unique across tenants, set on the Numbered codes page by `inventory:manage` and locked once any numbered code exists, because printed labels and NFC tags carry it), and the number is zero-padded to three digits and keeps counting past 999 (`CSN-1000`). The hyphen is not in the random-code alphabet, so a tag URL with one is always a numbered code and one without is always random. The tenant still comes from the request host.

- **Generating and printing.** Items → **Codes** (`/portal/inventory/items/codes`, called Numbered codes before #1450) creates the next N codes (`generate_numbered_inventory_tags()`, at most 150 at a time, numbered under a lock on the tenant's row so concurrent batches never collide), prints a range (`?numbers=1-50`) on the same sheets as every other label with the full code in large type and the QR of its tag URL, copies any one code's URL for writing an NFC tag on an iPhone, and lists every code as free or on _item_. Reading the page is `inventory:view`; creating codes and setting the prefix are `inventory:manage`.
- **Assigning is always a person's choice.** The system never picks a code for an item: whoever is holding the item enters or scans the tag in hand. On an item's page, **Assign numbered code** (`inventory:manage`) takes `7`, `007`, `CSN-7`, `csn007` or `CSN-007` alike, or a scan; a prefix, if given, must be this tenant's. A code another item holds asks first ("CSN-017 is on _Burton helmet_. Move it here?"). An item holds at most one numbered code, so assigning a second frees the first. **Unassign code** is the manual escape hatch. An item that has been distributed, retired or lost can't take one. Intake accepts a free numbered code wherever it accepts a pre-printed blank, and binds it instead of generating a random code; an item that comes back after a handout is received as a new item and takes whatever free tag the person receiving it has.
- **Freed automatically.** Whatever sets an item's status to `distributed`, `retired` or `lost` — `record_event_distribution()` and the scanned distribution through it, a giveaway handout, a gear request, the item's own edit sheet — frees its numbered code in the same transaction (a trigger on `inventory_items.status`). Deleting an item frees it too. Random codes are never freed. Because the code only comes off in the database, the UI tells the person to take the physical tag off: each piece on a scanned distribution list says "Remove tag CSN-007 before it goes out", the checkout makes each one a required tick-off line (#1519), the success message after recording names every tag freed and the item it was on (`record_distribution_draft()` returns them; `released_numbered_inventory_tags()` answers for a single handout, tying each release to its movement), and the edit sheet says "Saving frees CSN-007" when a status change will.
- **Resolver.** `/portal/t/<code>` for an assigned numbered code redirects to the item, with "Add to current distribution" as for any code. A free one shows **Assign to an item** (an item search, `inventory:manage`) and **Receive a donation with this tag** (`finance:manage` or `inventory_intake:manage`). An unknown number, another tenant's prefix, and a reader with no access get the same not-found as an unknown random code.
- **History.** Every binding is kept (`inventory_item_tag_assignments`), so an item's history still shows that it held CSN-007, from when to when and why it came off, after the code has moved on.

**The Codes page (#1450).** Items → **Codes** lists every code in one place — numbered codes, the random asset tags on items, unused blanks and NFC serials (manufacturer barcodes are left out: they aren't ours to print, and one UPC covers many items) — below the numbered-code tools (prefix, Create codes, Print a range). The list is filtered and paged in the database (`inventory_tag_codes()`, security invoker, with the filtered total on every row) because codes grow without bound. Columns: the code, its kind (Numbered / Asset tag / Blank / NFC), its state (Free — a numbered code on no item; Blank — a random code on no item; On item; Retired), the item it is on, when its label was last printed, and when it was written to NFC. Filters — kind, state, never printed, not written to NFC, and a number range for numbered codes — live in the URL, so a filtered view can be shared. Search takes a code with the same forgiveness as assigning one (`7`, `csn7`, `CSN-007` all find CSN-007; `parseCodeSearch()` shares `parseNumberedTag()`) or an item's description. Row actions are icons with tooltips — copy tag URL, print label, mark written to NFC, history — and, for `inventory:manage`, a menu with assign (the tag page's item search), unassign, retire and restore. Rows are selected on the page, or "all matching" the filter, and printed, marked written or retired together (at most 150 at a time).

- **Print and reprint.** `?print=<tag id>,…` or `?print=filter` plus the list's filters is one print view for any mix of codes, on `LabelSheets` and `LabelToolbar`; `?numbers=` stays as an alias for a range. A code on an item prints the item's description and size; a numbered code prints the code alone, since its label outlives the item (#1444); a blank prints the code alone. Retired codes and NFC serials are left out. Reprinting always prints the same code; a lost label is replaced by printing the code again, never by generating a new one.
- **Printed and NFC-written.** `inventory_item_tags.last_printed_at` and `print_count` are set by `record_inventory_labels_printed()` when the toolbar's print button is pressed (just before `window.print()`), and when a Katasymbol label prints or its images are saved or shared — never by opening a print view, since nothing there says paper came out, which is why the page says "Last printed". Donations → Blank labels, a donation's labels, the items label page and the Codes page all record it, so the date is right wherever the label came from. `nfc_written_at`/`nfc_written_by` are set after Android Chrome's **Write NFC tag** succeeds, or by hand (**Mark written**, one row or in bulk) on an iPhone, where the tag is written in another app; `set_inventory_tags_nfc_written()` also takes a mark back. A numbered code keeps its mark across items, because the tag holds the code's URL. Both are operational metadata, set through security definer functions on `inventory:view` (printing also on `finance:manage` or `inventory_intake:manage`, who print from Donations), so reprinting needs no `inventory:manage`.
- **Retiring a damaged or lost code.** `retire_inventory_tags()` (`inventory:manage`) records `retired_at`, `retired_by`, `retired_reason` (`damaged` | `lost` | `other`) and an optional note. A numbered code on an item comes off it in the same call (release reason `retired`), and its number is never reused, since printed copies may still be out there. A blank is never bound at intake again. A random code on an item is refused: its label is reprinted instead, since the code is the item's identity. A retired code is refused everywhere a code is bound or resolved — `assign_numbered_inventory_tag()` (outcome `retired`), `create_donation_with_items()` ("was retired as damaged or lost"), `inventory_intake_scan()` (status `retired`), and `/portal/t/<code>` and every in-portal scanner (the shared lookup skips retired codes, so it is the same not-found as an unknown code). **Restore** (`unretire_inventory_tag()`, `inventory:manage`) covers "found it" and mistakes; both are in the audit trail.
- **Per-code history.** The history action opens a sheet from `inventory_tag_history()`: each item the code was on (from `inventory_item_tag_assignments`, or for a random code the moment it was bound), why it came off, and when its label was printed, written to NFC, retired and restored, read from `audit_log` by a security definer function that answers only for a tag in this tenant, to `inventory:view` — inventory readers can't read `audit_log` directly.

### Public gear availability

The public site shall let visitors browse a gallery of gear currently available (`status = available` and `intended_use = gear_library`), with filtering by category (grouped by category group), condition, and gender, and free-text search by description. The public read path must go through a dedicated, curated database view rather than a relaxed policy on the internal `inventory_items` table, so donor linkage, face value, notes, status, and movement history stay behind authenticated-only access regardless of how the public view's field list evolves.

### Public gear requests

From the gear library, a visitor adds available items to a cart and submits one request for all of them with their name, email, optional phone, Instagram handle and notes, and **how they want the items** (issue #1032): an in-person meetup, or — when the tenant offers it — shipping at the requester's own cost, which asks for a postal address and which of the tenant's configured payment methods they will use for the postage. The request is handled by a `security definer` RPC (`request_gear_items`) that atomically re-checks availability, validates the delivery choice against the tenant's `gear_requests.*` settings, records one **`gear_requests` header** (requester, delivery method, address, payment preference, notes, status) and one `inventory_movements` row per item (`movement_type = reserved`, `recipient_person_id`, `gear_request_id`), flips each `inventory_items.status` to `reserved`, and returns the request id. The notes belong to the request, not to the requester: `people.notes` is a staff-maintained directory field, and writing per-request text there (as the RPC originally did, #721) both overwrote staff notes on a returning requester and put the text beyond the reach of the gear retention clock. The handle (issue #1357) is the one field here that belongs to the _person_ rather than to the request: it lands on their `people` row, filling an empty column and never replacing one a staffer has corrected — the rule `resolve_or_create_person_by_email()` already applies to pronouns. A signed-in reader's contact fields arrive filled in from their own session, never from whether a typed address matches a directory record ([§5.23](constituent-accounts.md#523-constituent-accounts)). **A reader the application already knows submits a different function** (issue #1359): `request_gear_items_as_me()` takes the person from `auth.uid()` on the request host instead of resolving the typed email, which is the only thing that actually closes the duplicate-person path — prefill lands a linked requester on the right row only because the address it prefills is the one on the record, and editing it sends the request elsewhere. It is a separate function rather than an extra argument on the anonymous one, for the reason [§5.9](people.md#59-people-directory) gives for the event-registration pair; everything that is a property of the items or of the tenant's settings — the rate limit, the delivery validation, the all-or-nothing locking, the header and the movements — is one internal `create_gear_request()` underneath, so the two paths cannot drift. That reader is shown their own name and address rather than asked for them, and corrects either through `/my/details`: `gear_requests` carries no contact column for a per-request correction to travel on. **A visitor without an account is offered one afterwards**, in the receipt, on the same terms as the offer after an event registration and in the same words ([§5.23](constituent-accounts.md#523-constituent-accounts)). **Every request records an as-is acknowledgement** (issue #1367): the gear library gives donated equipment away permanently — `inventory_movements` has `received` and `distributed` and no `returned` — so the exposure is the inverse of a loan's, and handing somebody a pair of skis reads as vouching for them unless something says otherwise. An unticked, required box beneath a short summary in the platform's own words is that something, and it is taken on the public request rather than at pickup: half the recipients are shipped to and never stand in front of an organizer, and a box in the portal would be staff attesting on a recipient's behalf. `gear_requests.as_is_acknowledged_at` records when and `as_is_text` snapshots the wording shown, resolved server-side from `src/lib/gear-as-is.ts` against the tenant's lexicon and never sent by the client; `acknowledged_as_is()` refuses the request inside `create_gear_request()`, so both public paths and the headless API answer to it once. The same paragraphs are the `items-we-give-away` section of the platform's terms of use, and the request links that document only where the tenant serves one ([`docs/legal-basis.md`](../legal-basis.md)). **Gear handed out in person outside a request** never passed through the public form, so it is acknowledged at the handout instead, by the recipient themselves — never by staff on their behalf — through the checkout above (#1519, superseding #1367's "out of scope"). **A request made before the acknowledgement existed** reads "Not recorded", and staff with `inventory:manage` may **ask the requester to acknowledge it** by emailed link (#1518) — from the request detail, or for every such request at once from the Requests list, both disabled with the reason when there is no address or the organization's email is off. As with #1502's answers link, the link is a single-purpose capability, not a sign-in: a hashed token, mailed through `deliverEmail()` and listed in the request's messages, that opens the shared `/acknowledge` page showing the requester's first name, the items on the request and the current summary, and records `as_is_acknowledged_at`, `as_is_text` (resolved server-side), `as_is_typed_name` and `as_is_method = emailed_link`. It works for 30 days, until used, and dies at once if the request is cancelled or acknowledged meanwhile; asking again supersedes it. Staff still never attest for the requester. The list and the detail badge each such request "As-is not recorded", "As-is requested" or "As-is acknowledged". **A tenant may require a passphrase before anything goes in the cart** (issue #1536), off for every tenant by default. It is a shared gate code staff give out, not a credential: `gear_requests.passphrase_required`, `gear_requests.passphrase` (stored readable, returned by `get_gear_request_settings()` only to `inventory:manage`) and `gear_requests.passphrase_help_text`, written by `set_gear_request_passphrase()` from its own card on the Requests page. Browsing stays open; the first Add to cart opens a dialog that names the organization, says to contact it for the passphrase or for more details (linking `/contact`, or the public email where that page is off) and shows the help text. `check_gear_request_passphrase()` (anon, 10 per 15 minutes per address) answers yes or no, and a yes unlocks the cart for the browser session: the server keeps the verified word in an httpOnly session cookie, out of reach of page scripts, and sends it with the request; a refused submit clears it. The database is what enforces it: `create_gear_request()` compares it trimmed and case-insensitively and raises `PASSPHRASE_REQUIRED`, so the anonymous path (before any person is matched or minted), the signed-in path and the headless API all answer to it, with no bypass for an account. Changing the passphrase therefore fails the next submit from an already-unlocked browser, and the dialog asks again. `public_gear_request_settings` exposes only `passphrase_required` and the help text, never the passphrase. A reserved item drops out of the public gear catalog until it is handed over, or the request is cancelled, or a staff member releases it back to `available` through the existing inventory management flow.

After the response, two emails go out through the outbound-mail plumbing of [§5.x notifications](../technical-spec.md): the `gear_request` kind to opted-in `inventory:manage` holders, linking to the request; and a confirmation to the requester (kind `gear_request_confirmation`, no preference — they hold no account) restating the items and the delivery choice and carrying the tenant's meetup or shipping-and-payment instructions. The dashboard bell counts requests still in `new`.

Staff work the queue at `/portal/inventory/requests` (list, `?status=` filter, detail). The only amount anywhere is the postage: a shipping request moves `new → quoted → paid → fulfilled` through `set_gear_request_status()`, which records the quote, refuses a closed request, and on `cancelled` releases the items the request still holds; a meetup goes `new → fulfilled`. **While a request is open, staff can change what is on it** (#1527): the detail lists each item with its photo, linked to the item's own page, and `inventory:manage` can add an `available` gear library item (`add_gear_request_item()`, which reserves it exactly as the public cart does), remove one the request still holds (`remove_gear_request_item()`), and edit the notes (`set_gear_request_notes()`). Removal puts the item back to `available`, detaches its original `reserved` movement from the request (so every reader that lists a request's items by its `reserved` movements stops counting it, and a later cancellation cannot release somebody else's hold on it) and records the release as an `other` movement that still points at the request, so the item's history says which request it left. The last item cannot be removed: an empty request is a cancellation, and cancelling says so. Notes are the requester's own text and they read them back in their account, so a staff edit is visible to them. Payment itself is taken outside the system (Zelle, Venmo — whatever the tenant lists), record-only, the same policy as sales. Which delivery methods are offered, the accepted payment methods with their handles, and the instruction text are the tenant's `gear_requests.shipping_enabled`, `gear_requests.payment_methods`, `gear_requests.meetup_instructions` and `gear_requests.shipping_instructions` settings, edited on the Requests page under `inventory:manage`; the public form reads only the first two, and only the methods' keys and labels, through the `public_gear_request_settings` view. The shipping address is redacted from `audit_log` (`audited_tables.redacted_columns`) and cleared, with the requester link, payment preference and notes, by the `gear_requests` retention rule three years after the handover.

**Writing to the requester** (issue #1203). The request detail carries a Messages card and two actions behind `inventory:manage`: **Contact requester**, which sends one message the staffer types — the substitution, the Saturday, the postage, the conversation that used to happen in somebody's personal mailbox and left the record missing half its history — and **Resend confirmation**, which re-renders the original receipt for a requester who never received it (every request taken before #1032 shipped got none). Each send is one row in `outbound_messages`, listed in the card with who sent it, when, and whether the provider took it.

Four things that shape the design. The message goes out from the tenant's own sender with the tenant's Reply-To, and **replies leave the platform** for that mailbox — the composer says so, because there is no inbox in the portal to read them in. The address is never in the message body: the recipient is resolved from the request by the Server Action, so nothing the browser sends decides who is written to. `staff_message` is deliberately **not** a notification kind, so a requester who switched every receipt off still hears back — see [§5.9](people.md#59-people-directory) for why correspondence and subscriptions are governed differently; the org-wide email switch still stops it. And a resend varies its dedupe key by the minute, so a second copy can be sent tomorrow while a double-click today is one email.

`outbound_messages` is polymorphic (`module`, `record_type`, `record_id`) and read through `has_permission(module, 'manage')`, so the same primitive serves other queues (#1204) without another policy. `subject`, `body` and `to_email` are redacted from `audit_log` — the trail records that a message went out, never what it said — and all four, with the requester link, are cleared by the `outbound_messages` retention rule two years after the send.

## 5.7 Donations

The initial inventory workflow is the primary way administrators manage donated gear. Donation records should retain donor and donation context where needed, while inventory records retain the item-level details. Donor personal information must be restricted to authorized users with a legitimate operational need.

## 5.13 Open questions

- **Volunteer-facing donation/distribution recording**: recording a donation or distribution from an event should be quick and easy for a volunteer to reach in the field, not just from the main inventory workflow.
- **Quick edit from the events list**: editing a donation/distribution via the events list may only need to collect a number and notes tied to the event, rather than the full inventory workflow.
- ~~**Giveaway prizes drawn from in-kind donations**~~: **decided** (issues #520, #570) — a donated item used as a prize stays on the standard inventory path rather than getting a giveaway-specific one. The prize references the `inventory_items` row, and allocating it reserves the item and writes an `inventory_movements` row, so receipt, status and movement history all behave as they do for any other reservation. See [§5.8](giveaways.md#58-giveaways).

## 5.19 Inventory valuation reporting

Authorized users (`admin`, and `finance`/`board` for view-only oversight per [§5.3](access-control.md#53-authentication-and-authorization)) shall be able to view a valuation report over existing inventory data:

- Total face value of on-hand inventory, by category and status.
- Value donated and value distributed over a selected period, derived from `inventory_movements`.

This is a reporting view over `inventory_items` and `inventory_movements` — no new tables are required.

**Implemented.** `/portal/inventory/reports` computes on-hand face value by category/status and value donated/distributed over a selected period directly from `inventory_items.face_value` and `inventory_movements` (received/distributed movement types) — no new tables. Since issue #667 the category breakdown groups on the vocabulary rather than on the raw free-text string, and leads with a category-group roll-up, so one real category can no longer appear as several rows.

## 6. Data model — Inventory and donations

- `people`: shared directory of donors, sponsors, volunteers, staff, partners and gear recipients (name, email, phone, notes), so the same contact can be reused across roles instead of being duplicated per context. It carries **no role columns**: role membership is derived by `public.people_with_roles` ([§5.9](people.md#59-people-directory)), the view every read site uses, from the records that create each role unioned with `person_role_tags`. A role is therefore never stale — it appears with the record behind it and goes away with the last one. What the seven roles are _called_ is tenant data (`people.role_labels`, #911; [§5.9](people.md#59-people-directory)) — the keys here are not. `person_type` (`individual` | `organization`, issue #625) is the separate, exclusive axis: it is staff-asserted rather than derived and decides the shape of the record — an organization has a logo, a website, a primary contact and org memberships, an individual has a rider profile — so the person form renders one branch or the other off it. A further type (`household`, for family registrations) is a check-constraint change rather than another boolean.
- `donations`
- `donation_items`
- `inventory_items`: donation-managed inventory records with description, `category_id` (FK to `inventory_categories`, `on delete restrict`; nullable, where null means a legacy row nothing matched), size, gender, condition, face value, photo, status, and `intended_use` — what the item is _for_ (`gear_library`, `giveaway`, `internal`), as distinct from where it is in its lifecycle (`status`)
- `inventory_movements`: receipt, distribution, adjustment, and retirement transactions; a reserved movement from the public library points at its request through `gear_request_id` (#1032) — detached when staff remove the item, whose release is an `other` movement carrying the request id (#1527); a movement recorded by an in-person handout points at its `distribution_acknowledgements` row through `distribution_acknowledgement_id` (#1519; composite FK, set null)
- `distribution_acknowledgements`: the as-is acknowledgement taken from the recipient at an in-person handout, or why there is none (#1519) — `recipient_person_id` (composite FK to `people`, set null), `present_staff` (the user running the checkout), and either `acknowledged_at`/`as_is_text` (the summary shown, resolved server-side)/`typed_name`/`method` (`own_device` | `staff_device` | `emailed_link`) or `skipped_reason` (`left_before_acknowledging` | `no_phone` | `declined_to_wait` | `other`)/`skipped_note` — never both, except that a skipped handout acknowledged afterwards by emailed link keeps its reason beside the acknowledgement, with method `emailed_link` (check constraint). Written only by `record_distribution_draft()` and, for the emailed link, `acknowledge_as_is_by_token()`; select on `inventory:view`. Audited with `typed_name` redacted, and in `retention_purgeable_person_refs`. As with `gear_requests.as_is_*`, when, what was shown and how survive anonymization; the purge's rule E3 clears the recipient link and the typed name on the gear-request clock. `inventory_item_history()` returns the acknowledgement (or the request's, as method `gear_request`, for a handout that skipped the step) on each distribution entry
- `inventory_item_tags`: scannable carriers of an item's identity (#1420) — `item_id` (composite FK to `inventory_items`, cascade; null only for an `asset_tag` printed before its item exists or a free `numbered` code), `kind` (`asset_tag` | `barcode` | `nfc` | `numbered`), `value`, and `number` (#1444; set for `numbered` only, which a trigger allocates from the tenant's highest under a lock on its row and formats with the tenant's prefix — a numbered code is never renumbered, changed to another kind or deleted by a session). Unique per tenant on `number`, and one `numbered` code per item. An `asset_tag` inserted with an empty value gets a generated code from a trigger, and `asset_tag` and `nfc` values are stored upper case. Unique per tenant on `(kind, value)` for `asset_tag` and `nfc`, and one `asset_tag` per item; `barcode` is not unique, since one UPC can cover many pieces. Select on `inventory:view`, writes on `inventory:manage`; audited with nothing redacted. Since #1450 also `last_printed_at` and `print_count` (set by `record_inventory_labels_printed()`), `nfc_written_at`/`nfc_written_by` (`set_inventory_tags_nfc_written()`; `asset_tag` and `numbered` only), and `retired_at`/`retired_by`/`retired_reason` (`damaged` | `lost` | `other`)/`retired_note` (≤ 500 characters; `retire_inventory_tags()` and `unretire_inventory_tag()`, `inventory:manage`). A retired code is always on no item and is an `asset_tag` or `numbered` code (check constraints). The Codes page reads the table through `inventory_tag_codes()` and one code's history through `inventory_tag_history()`
- `inventory_item_tag_assignments`: each time a numbered code (#1444) was on an item — `tag_id` and `item_id` (composite FKs, cascade), `assigned_at`/`assigned_by`, `released_at`/`released_by`, and `release_reason` (`distributed` | `retired` | `lost` | `moved` | `replaced` | `unassigned`). At most one open row per tag. Written only by the trigger on `inventory_item_tags.item_id`, so it cannot disagree with the tag; select on `inventory:view`, no client writes; audited. Read by `inventory_item_history()` as `tag_assigned` and `tag_released` entries
- `tenants.inventory_tag_prefix` (#1444): three upper-case letters, unique across tenants, starting every numbered code; set through `set_inventory_tag_prefix()` (`inventory:manage`) and locked by a trigger once the tenant has a numbered code
- `inventory_distribution_drafts` / `inventory_distribution_draft_items`: a person's in-progress scanned distribution (#1420) — one draft per `(user_id, event_id)` with `nulls not distinct`, so the no-event list is one too; items by composite FK to `inventory_items`, unique per draft. Owner-only RLS that also requires `inventory:manage` or `inventory_intake:manage` (the same gate as `record_event_distribution()`). A draft keeps its `recipient_person_id` (#1443; composite FK to `people`, set null when the person is deleted), set by `set_distribution_draft_recipient()`, which `record_distribution_draft()` uses when no recipient is passed; `move_distribution_draft()` moves a draft to another event, merging it into one already there. Filled by `add_to_distribution_draft()` and turned into movements, then deleted, by `record_distribution_draft()`. Not audited: a draft records nothing, and the movements it becomes are audited where they land. Since #1519 a draft also carries the handout's pending acknowledgement — `ack_token_hash` (SHA-256 of the one-time QR token; outside the select grant), `ack_token_expires_at`, `ack_acknowledged_at`, `ack_as_is_text`, `ack_typed_name`, `ack_method` (`own_device` | `staff_device`) — outside the owner's insert and update grants, written only by `issue_distribution_acknowledgement_token()`, `acknowledge_distribution_by_token()` (anon, rate-limited) and `acknowledge_distribution_on_staff_device()`, and cleared by a trigger when `recipient_person_id` changes
- `gear_request_acknowledgement_requests`: the emailed link asking a requester to acknowledge as-is (#1518) — one row per request (`unique (tenant_id, request_id)`, composite FK, on delete cascade), `token_hash` (SHA-256 of the mailed token; outside the select grant), `expires_at` (30 days), `requested_at`/`requested_by`, `acknowledged_at`. Asking again overwrites the hash. Select on `inventory:view`; written only by `request_gear_request_acknowledgements()` (`inventory:manage`) and `acknowledge_as_is_by_token()`. `get_as_is_acknowledgement()` and `acknowledge_as_is_by_token()` (anon, rate-limited) are the one pair behind `/acknowledge` for this link and a handout's one-time code alike. Not audited and holds no personal data
- `distribution_acknowledgement_requests`: the emailed link asking a handout's recipient to acknowledge as-is after it was recorded with a reason (#1519) — one row per handout (`unique (tenant_id, acknowledgement_id)`, composite FK to `distribution_acknowledgements`, on delete cascade), `token_hash` (SHA-256 of the mailed token; outside the select grant), `expires_at` (30 days), `requested_at`/`requested_by`, `acknowledged_at`, `gear_request_ids` (pre-#1367 meetup requests the handout fulfilled, written back to when it is followed). Select on `inventory:view`; written only by `record_distribution_draft()` (its `p_link_token_hash`) and `acknowledge_as_is_by_token()`, and deleted when the send fails. `get_as_is_acknowledgement()` looks a token up as a gear-request link, then a handout link (`kind: handout_link`), then a handout's one-time code. Not audited and holds no personal data
- `gear_requests`: one public library request (#1032) — `person_id` (composite FK to `people`, nulled by retention), `delivery_method` (`meetup` | `shipping`), the flattened `ship_*` address columns, `payment_method` (the key of one of the tenant's configured methods), `notes`, `as_is_acknowledged_at`/`as_is_text` (#1367 — when the requester acknowledged that items are given as-is, and the wording they were shown; neither is redacted in the audit trail nor cleared by retention, since they are the organization's own published words and a fact about an act rather than personal data), and `as_is_method` (`request_form` | `emailed_link` | `in_person`, #1519; null exactly when the acknowledgement is, defaulted to `request_form` on insert), `as_is_typed_name` (#1518 — the name typed on the emailed link; personal data, so redacted in the audit trail and cleared by a trigger when `person_id` goes null, which covers retention rule E2), `status` (`new` | `quoted` | `paid` | `fulfilled` | `cancelled`), `quoted_amount`/`quoted_at`, `paid_at`, `fulfilled_at`, `cancelled_at`. Select on `inventory:view`; no client insert, update or delete — `request_gear_items()` inserts, `set_gear_request_status()` moves it, and `set_gear_request_notes()`, `add_gear_request_item()` and `remove_gear_request_item()` edit an open one (#1527). Registered in `audited_tables` with the address and notes redacted, and in `retention_purgeable_person_refs`
- `public_gear_request_settings`: `security definer` view granted to `anon` exposing four of the resolved tenant's `gear_requests.*` settings — whether shipping is offered, the accepted payment methods as key and label only, whether a passphrase is required and its help text (#1536; never the passphrase)
- `person_role_tags`: manual role assertions (`person_id`, `role`, `granted_at`, `granted_by`, `notes`, `is_public`) — the half of the derived role model no source record backs, such as a sponsor entered in the directory before any event link exists. Unlike a boolean it carries when the role was asserted and by whom. `is_public` (#1024) is meaningful on the `sponsor` role alone, the only one with a public surface: it publishes an _organization_ to the sponsor wall on `/support/sponsorship` with no event anywhere, the second opt-in beside `event_sponsors.is_public` ([§5.5](events.md#55-event-management)). It defaults false, `set_person_role_tags` refuses a public role it was not also asked to assert, and `merge_people` carries a published duplicate's flag onto the survivor before dropping the redundant tag (#1030) — a merge never takes an organization off the public site
- `people_with_roles`: `security_invoker` view over `people` adding the seven derived role flags via the `security definer` helper `person_role_flags()` ([§5.9](people.md#59-people-directory)); granted to `authenticated` only, and read-only — writes go to `people`. The flags are named for the platform's vocabulary; what a tenant calls each role is `people.role_labels` (#911) and never reaches this shape
- `public_gear_catalog`: read-only view over `inventory_items` limited to `status = available` **and** `intended_use = gear_library` rows and a curated column set (description, size, type, gender, condition, photo, plus the item's category/group keys, labels and sort orders); granted to the `anon` role so it can back the public gear gallery without relaxing RLS on the base table. The category labels are denormalized into the view on purpose, so `anon` needs no access to the vocabulary tables themselves
- `inventory_category_groups` / `inventory_categories`: the two-level controlled item-category vocabulary (issue #667) — `key` (stable machine token, never changed by a rename), `label`, `sort_order`, `is_active`. Readable by any signed-in user (an intake volunteer holds `inventory_intake:manage` but `inventory:none`, and still has to render the picker); editable with `inventory:manage` at `/portal/inventory/categories`; both registered in `audited_tables`. `resolve_inventory_category(text)` maps free text to a category by key, label or a known alias, and backs both the one-time backfill and a `before insert` trigger on `inventory_items` that classifies rows written by callers that still supply only `type`
- `inventory_items_with_category`: `security_invoker` view over `inventory_items` left-joined to the vocabulary, adding `category_key`/`category_label`/`category_group_key`/`category_group_label` and a `category_sort_key`. It exists because the items list is server-sorted by category and PostgREST cannot order a row by an embedded resource's column
- `inventory_photos`
- `distribution_recipients`: protected recipient records, if needed
